6## Abstract
7
8This specification defines a message and event catalog extension to the
9xRegistry document format and API [specification](./../../core-v1/docs/spec.md). The
10message definitions registry service (or "message catalog") allows for
11declaring the metadata (headers, properties, attributes) of messages and/or
12events and their relationships to schemas, and for grouping those declarations
13such that they can be associated with endpoints. With the help of this
14metadata, users can provide constraints for messaging channels, declaring
15precisely which messages or events are permitted to be sent or can be expected
16to be received, and how these messages can be distinguished.

72## Overview
73
74The goal of this message metadata model, in conjunction with the [endpoint
75model](./../../endpoint-v1/docs/spec.md), is to provide metadata structure to asynchronous
76topics, streams and queues in a way that is similar to how table and column
77definitions provide structure to databases. Database schemas structure data
78that you have. Endpoint definitions with their referenced, or embedded message
79definitions, with referenced, or embedded, schema definitions structure data
80that will be transmitted.
81
82Continuing that analogy, the endpoint scope corresponds to the database, the
83message groups are schema scopes, and the message definitions correspond to
84tables. The schema associated with a message definition determines the column
85layout of the table. As event streams often end up landing in databases for
86long-term archival and analysis, this structural alignment is very helpful.
87
88Managing the description of the payloads of those messages and events is not in
89scope, but delegated to the [schema registry extension](./../../schema-v1/docs/spec.md) for
90xRegistry. Schemas are linked from messages and event declarations through a
91URI Reference.
92
93### Message Definitions
94
95A Message Definition ("message") describes constraints for the metadata of a
96message or event. It declares, for instance, the concrete values or
97permissible value patterns for the `type`, `source`, and `subject` attributes
98of a CloudEvent.
99
100A message definition has two key purposes:
101
1021. A message definition is a template. When an application needs to raise an
103 event, the message definition declares precisely which attributes,
104 headers or properties need to be set on the event envelope or on the
105 protocol message, and which constant values are to be set, or which type of
106 pattern constraints apply. Such templates can be evaluated by tools and
107 code generators, which can then create an interface or event factory for
108 the application programmer that minimizes opportunities to introduce
109 mapping errors.
110
1112. A message definition is a filter condition. When an application needs to
112 demultiplex an incoming stream, messages, or events that come through the
113 same channel, it can use a collection of message definitions as a set of
114 candidate messages that are expected and can be handled. The metadata of
115 the incoming events or messages is tested against the declarations of the
116 candidate definitions, attribute by attribute, yielding none, one, or more
117 matches for the incoming message. If there is no match, the incoming
118 message is unexpected and will likely be sidelined. If there is one match,
119 the message can be passed on to the application. If there are multiple
120 matches, the message might be evaluated further by matching the body
121 content against the associated data schema.
122
123For message and event producers, the template aspect is the primary concern.
124Following the declared rules, including validating the payload against the
125associated schema, ensures that all consumers receive messages with the
126expected content.
127
128For message and event consumers, the filter aspect is the primary concern.
129Consumer applications and frameworks can rely on the declared message metadata
130to demultiplex and dispatch messages and events to handlers and they can
131sideline non-conformant messages, for instance into dead-letter queues.
132
133### Message Metadata
134
135Any message definition covers up to three aspects:
136
1371. Envelope: An `envelope` is a transport independent metadata convention that
138 lets a producer convey the context of an event or message to consumers or
139 intermediaries (like publish/subscribe routers) without them having to
140 understand the particular payload format or having to read the payload. The
141 only predefined envelope model in this specification is CNCF CloudEvents
142 1.0. Once the `envelope` selector is set, constraints for the attributes
143 of the CloudEvents envelope can be defined in the `envelopeoptions`.
144
1452. Protocol: The `protocol` selector picks a specific application protocol to
146 which the given message is bound. If a protocol is chosen, constraints for
147 the protocol-specific message model can be defined in `protocoloptions`.
148 For instance, if you choose the `MQTT/5.0` protocol, you can constrain the
149 topic path to which this message can be sent and/or the quality-of-service
150 QoS level that is to be used. This specification covers the full metadata
151 set of the application protocols AMQP/1.0, MQTT/3.1.1, MQTT/5.0, Kafka,
152 NATS, and HTTP.
153
1543. Payload: The `dataschema*` and `datacontenttype` attributes declare the
155 content type of the payload and a schema that can be used to construct,
156 validate, decode and/or encode the payload. The `dataschemaformat`
157 declaration selects the kind of schema (e.g. XML Schema, Protobuf, Avro or
158 others) that is embedded at or referenced by the chosen `dataschema*`
159 attribute.
160
161A `message` definition MAY contain any combination of `envelope`, `protocol`,
162and data payload declarations. A payload-only declaration can be useful if
163messages are sent through varying protocols without a fixed envelope model and
164are distinguished by content-type (including parameters) or even only through
165whether payload schema definitions match an incoming message.
166
167Where attributes (or properties or headers; depending on protocol nomenclature)
168can be defined in the `envelopeoptions` and `protocoloptions`, the general
169pattern used in this model is that the attribute can have a name, a
170description, a type and a value. Setting a value makes that value constant for
171all instances of that message, which is useful for discriminators like AMQP’s
172subject property or CloudEvents’ type attribute.
173
174The `uritemplate` type permits the values to have embedded placeholders (Level
1751 URI templates), which turns the values into templates for publishers where
176the application inserts context information into designated places. For
177consumers, the templates act as pattern-matching filters and extract
178context values into named variables.
179
180### Context Attributes
181
182The embedded placeholders in values of the `uritemplate` type can refer to
183context attributes provided by the application environment in which the metadata
184is evaluated. For instance, a message definition might declare a `source`
185attribute in the `envelopeoptions` of a CloudEvent, with a `uritemplate` type
186and a `value` definition `/vehicles/{vin}/systems/{system}/sensor/{sensor}`.
187
188If the application environment from which the message is published provides values
189for the `vin`, `system`, and `sensor` context attributes, those values can be
190easily inserted into the URI template when the message is published. Reversely,
191if a message is received with a URI that matches the template, the values can
192be extracted and made available as context attributes.
193
194A further use of such context attributes is the mapping of protocol-native
195messages to CloudEvents. An application evaluating message definitions that
196contain both a `protocol` and an `envelope` definition might nevertheless
197choose to accept protocol-native messages that are not CloudEvents and then
198use context attributes to map them to the CloudEvents model.
199
200For example, let there be this definition:
201
202```json
203{
204 "protocol": "MQTT/5.0",
205 "protocoloptions": {
206 "topic_name": "/store/{storeid}/cashierdesk/{cdid}"
207 "user_properties" : [
208 { "name": "eventType", "type": "uritemplate", "value": "{eventType}" }
209 ]
210 },
211 "envelope": "CloudEvents/1.0",
212 "envelopeoptions": {
213 "type": { "type": "uritemplate", "value": "{eventType}" },
214 "source": { "type": "uritemplate", "value": "{storeid}" },
215 "subject": { "type": "uritemplate", "value": "{cdid}" }
216 }
217}
218```
219
220An application might use this definition to match incoming MQTT messages only
221against the `protocol`/`protocoloptions` part of the definition. If an incoming
222message matches this part, the application can then use the `envelope` and
223`envelopeoptions` definitions to transform the message into a CloudEvent, with
224the context attributes carrying the values.
225
226Context attributes and their handling are not covered by the following normative
227part of this specification.
228
229### Reusing Message Definitions
230
231In complex event-driven enterprise applications it might be desirable to reuse
232common definitions across different applications. There might also be a need
233to route the same set of CloudEvents through a specific protocol route, like
234MQTT, where it would be useful to provide protocol-specific hints in addition
235to the CloudEvents declaration like requiring a specific topic path pattern
236for the event type.
237
238The `basemessage` attribute, a URI-typed reference to another message
239definition, enables such reuse scenarios. Any message definition MAY refer to
240another message definition as its base, which effects a copy of the base
241message’s definitions into the message that defines it. The mechanism is
242transitive, which means that `basemessage` relationships MUST be resolved
243recursively as long as they do not result in circular references.
244
245All aspects of the collected base message are "shadowed" by the definitions of
246the message that references it. If the base message defines an "envelope" but
247no "protocol", the new definition can add the aforementioned MQTT aspects with
248a new "protocol" selector and corresponding options.
249
250```mermaid
251flowchart TB

259 end

273### Message Definition Matching
274
275One popular use of a Message Registry is to be a catalog of Message definitions
276that are used to validate incoming messages. In these scenarios, the receiver
277of a message might need to "match" it to the corresponding Message definition
278that the message is meant to adhere to. This specification does not mandate how
279this "matching" is done. For example, matching headers or schema of the
280incoming message to the Message definitions in the Registry is one option.
281
282A Registry with many Message definitions, each potentially having
283multiple Versions, results in a 2-dimensional collection of Message
284definitions to match against, which could make finding the exact Message
285definition complex, non-deterministic or very slow. To help with these
286situations, this specification provides the following guidance:
287
288- Use of CloudEvents is RECOMMENDED as it will provide well-defined
289 metadata that will appear in each Message to help differentiate Message
290 definitions.
291- Message definitions SHOULD have a `messageid` value that is the same as the
292 CloudEvents' `type` context attribute defined for that Message. This will
293 allow for an exact mapping from the incoming Message's `type` attribute to
294 its related Message definition.
295- Message Resource types SHOULD be defined with a `maxversions` of `1`. This
296 eliminates the need for each incoming Message to include some unique
297 Version discriminator.
298- Modifications to Message definitions SHOULD NOT result in "on the wire"
299 changes to the resulting messages as that could break existing systems.
300 Rather, new Message definitions SHOULD be created, with new `type` and
301 `messageid` values, and referenced through the use of the `deprecated`
302 attribute.
303
304Implementations and Registry model authors MAY deviate from these
305recommendations; however, they are then responsible for defining the
306mechanisms by which a unique Message definition is matched to incoming
307messages.

309## Message Groups
310
311All message definitions MUST be contained in a group. A message group can be
312formed for many reasons. At a minimum, the group will be an access control
313boundary in many implementations of this specification even though none is
314mandated.
315
316In many cases, message groups will be a logical boundary around a set of
317related events that are commonly routed through the channel. A (primitive) air
318travel luggage handling system might have "checkedin", "loaded", "unloaded",
319and "delivered" events related to items it moves. If those are reported to
320external parties through the same channels, it likely makes sense to group
321them.
322
323A benefit of message groups is that they are very similar to "interfaces" in
324common programming languages. When a message group is associated with a
325channel, like a queue, the messages contained in the group form the permitted
326and expected message set. The association becomes a contract.
327
328This association is formalized in the [Endpoint Registry](./../../endpoint-v1/docs/spec.md),
329a related registry that allows associating one or more message definition
330groups with an endpoint, thus effectively defining a contract for the endpoint.
331An "endpoint" as defined in that specification is also a message definition
332group in itself, with the message definitions following the rules of this
333specification.
334
335When message definitions are to be recombined into different groups, the
336original message definitions can be referenced instead of copied. For
337instance, a pubsub topic might take 4 messages as input but a filtering
338subscription might only yield 1 of those messages as output. In this case, one
339would create a distinct message group for the subscription and "xref" the
340message definition from the input group (sample to follow in the merged doc).
341
342Similarly, one could create a new message group to be associated with an MQTT
343endpoint if the messages annotate CloudEvent definitions with MQTT protocol
344options using the "basemessage" mechanism. (sample also to follow)

348### Notational Conventions
349
350The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
351"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
352interpreted as described in [RFC 2119](https://tools.ietf.org/html/rfc2119).
353
354For clarity, OPTIONAL attributes (specification-defined and extensions) are
355OPTIONAL for clients to use, but the servers' responsibility will vary.
356Server-unknown extension attributes MUST be silently stored in the backing
357datastore. Specification-defined attributes and server-known extension
358attributes MUST generate an error if the corresponding feature is not supported
359or enabled. However, as with all attributes, if accepting the attribute results
360in a bad state (such as exceeding a size limit or resulting in a security
361issue), then the server MAY choose to reject the request.
362
363In the pseudo JSON format snippets `?` means the preceding attribute is
364OPTIONAL, `*` means the preceding attribute MAY appear zero or more times,
365and `+` means the preceding attribute MUST appear at least once. The presence
366of the `#` character means the remaining portion of the line is a comment.
367Whitespace characters in the JSON snippets are used for readability and are
368not normative.

370### Terminology
371
372This specification defines the following terms:
373
374#### Message and Event
375
376A **message** is a transport wrapper around a **message body** (interchangeably
377referred to as payload) that is decorated with **metadata**. The metadata
378describes the message body without an intermediary having to inspect it and
379carries further information useful for identification, routing, and
380dispatching.
381
382In this specification, **message** is an umbrella term that refers to all kinds
383of messages as well as to **events** as a special form of messages.
384
385The definition of [message][message] from the CloudEvents specification
386applies.
387
388#### Envelopes and Protocols
389
390An **envelope** is a transport protocol-independent message metadata
391convention. The [CNCF CloudEvents][CloudEvents] specification is an example of
392a message envelope and is the only envelope explicitly defined in this
393specification.
394
395A similar transport protocol-independent message metadata convention is, for
396example, the [W3C SOAP 1.2 envelope][SOAP] for which support could be added by
397an extension.
398
399This specification uses **protocol** as a selector into the protocol-specific
400message metadata that is defined under the `protocol.ifvalues` section of the
401model. When a known protocol is explicitly specified for a message definition,
402the `protocoloptions` section MAY contain constraints for the
403protocol-specific metadata.

520### Message Definition Groups
521
522The Group plural name (`<GROUPS>`) is `messagegroups`, and the Group singular
523name (`<GROUP>`) is `messagegroup`.
524
525The following attributes are defined for the `messagegroup` object in addition
526to the xRegistry-defined core
527[attributes](./../../core-v1/docs/spec.md#attributes-and-extensions):
528
529#### `envelope` (Message Group)
530
531- Type: String
532- Description: Identifies a common, transport protocol-independent message
533 metadata format. Message metadata envelopes are referenced by name and
534 version as `<NAME>/<VERSION>`. This specification defines a set of common
535 [metadata envelope names](#metadata-envelopes) that MUST be used for the
536 given envelopes, but applications MAY define extensions for other envelopes
537 on their own. All messages inside a group MUST use this same envelope.
538- Constraints:
539 - If present, MUST be a non-empty case-insensitive string.
540 - If present, MUST follow the naming convention `<NAME>/<VERSION>`, whereby
541 `<NAME>` is the name of the metadata envelope and `<VERSION>` is the
542 version of the metadata envelope.
543- Examples:
544 - `CloudEvents/1.0`
545
546#### `protocol` (Message Group)
547
548- Type: String
549- Description: Identifies a transport protocol to be bound to for this Message.
550 Protocols are referenced by name and version as `<NAME>/<VERSION>`. This
551 specification defines a set of common [message protocol
552 names](#message-protocols) that MUST be used for the given protocols, but
553 applications MAY define extensions for other protocols on their own. All
554 messages inside a group MUST use this same protocol.
555- Constraints:
556 - If present, MUST be a non-empty case-insensitive string.
557 - If present, MUST follow the naming convention `<NAME>` or
558 `<NAME>/<VERSION>`, whereby `<NAME>` is the name of the protocol and
559 `<VERSION>` is the version of protocol. The version is REQUIRED if
560 multiple, mutually incompatible versions of the protocol exist and
561 protocol options differ between versions.
562- Examples:
563 - `MQTT/3.1.1`
564 - `AMQP/1.0`
565 - `KAFKA`

567### Message Definitions (Message Group)
568
569The Resource plural name (`<RESOURCES>`) is `messages`, and the Resource
570singular name (`<RESOURCE>`) is `message`.
571
572Different from schemas, message definitions do not contain a
573version history. If the metadata of two messages differs, they are considered
574different messages.
575
576When [CloudEvents](https://cloudevents.io) is used for a particular
577message, it is RECOMMENDED that the message's `messageid` attribute be the
578same as the [CloudEvents `type`
579attribute](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md#type).
580Doing so makes for easier management of the meta-model by correlating
581the look-up value (id) of messages with their related events.
582
583The following extensions are defined for the `message` Resource in addition to
584the core xRegistry Resource
585[attributes](./../../core-v1/docs/spec.md#attributes-and-extensions):
586
587#### `basemessage`
588
589- Type: URI
590- Description: if present, the URI points to a message definition that is the
591 base for this message definition. By following the reference, the base
592 message can be retrieved and extended with the properties of this message.
593 This is useful for defining variants of messages that only differ in minor
594 additive aspects to avoid repetition. For example, this applies to messages
595 that only have an `envelope` with associated `envelopemetadata` to be bound
596 to various protocols.
597
598 When the value is a relative reference (begins with `/`), it MUST be a
599 valid XID referencing a Resource, or Version, of type `message` within the
600 same registry. When the value is an absolute URI, it MUST point to a
601 message definition in an external registry, but the server is not mandated
602 to validate or resolve external references.
603
604 Referenced messages MAY themselves have a `basemessage` value; however,
605 the chain of messages MUST NOT be recursive.
606
607 The process that a client SHOULD follow to materialize the message is
608 to follow the `basemessage` references to the end of the chain of messages,
609 get that message's attributes, and then walk back up the chain performing a
610 "merge" operation of the next message's attributes. Note that if an
611 inherited attribute is a complex type (e.g. map, object) and the overlaying
612 attribute is scalar, then the entire inherited attribute (and nested
613 values) are replaced by that scalar value. For complex types, the
614 merge is "deep", meaning each level of the complex type is merged
615 appropriately rather than it being a complete replacement of the entire
616 complex type.
617
618 If the referenced message can not be found, whether due to a dangling
619 reference, an unreachable external registry, or insufficient permissions,
620 an error MUST NOT be generated. Dangling references are permitted.
621
622 Resolution of absolute URIs is a client responsibility. The server stores
623 the URI value but is not mandated to fetch, validate, or cache external
624 message definitions.
625
626- Constraints:
627 - OPTIONAL.
628 - If the value is a relative reference, it MUST be a valid `xid` of a
629 Resource, or Version, of type `message` as defined by this specification.
630 - If the value is an absolute URI, it MUST point to a message definition
631 but the server MUST NOT validate the target.
632
633- Examples:
634 - `/messagegroups/group1/messages/msg1`
635 - `/messagegroups/group1/messages/msg1/versions/v1.0`
636 - `https://catalog.example.com/messagegroups/shared/messages/base-event`
637
638#### `envelope`
639
640Same as the [`envelope`](#envelope-message-group) attribute of the
641`messagegroup` object.
642
643Since messages MAY be cross-referenced ("borrowed") across message group
644boundaries, this attribute is also REQUIRED and MUST be the same as the
645`envelope` attribute of the `messagegroup` object into which the message is
646embedded or referenced.
647
648Illustrating example:
649
650```yaml
651"messagegroupsurl": "...",
652"messagegroupscount": 2,
653"messagegroups": {
654 "com.example.abc": {
655 "messagegroupid": "com.example.abc",
656 "envelope": "CloudEvents/1.0",
657
658 "messagesurl": "...",
659 "messagescount": 2,
660 "messages": {
661 "com.example.abc.event1": {
662 "messageid": "com.example.abc.event1",
663 "envelope": "CloudEvents/1.0",
664 # details ...
665 }
666 },
667 "com.example.abc.event2": {
668 "messageid": "com.example.abc.event1",
669 "envelope": "CloudEvents/1.0",
670 # details ...
671 }
672 },
673 "com.example.def": {
674 "messagegroupid": "com.example.def",
675 "envelope": "CloudEvents/1.0",
676
677 "messagesurl": "...",
678 "messagescount": 1,
679 "messages": {
680 "com.example.abc.event1": {
681 "uri": "#/messagegroups/com.example.abc/messages/com.example.abc.event1",
682 # details ...
683 }
684 }
685 }
686}
687```

689#### `envelopemetadata`
690
691- Type: Object
692- Description: Describes the metadata constraints for messages of this type.
693 The content of this property is defined by the message `envelope`, but all
694 envelopes use a common schema for the constraints defined for their
695 metadata headers, properties or attributes.
696- Constraints:
697 - REQUIRED if `envelope` is specified.
698- Examples:
699 - See [Metadata Envelopes](#metadata-envelopes)
700
701#### `envelopeoptions`
702
703- Type: Map
704- Description: Configuration details of the Message with respect to the
705 envelope format used to format the messages. See
706 [Metadata Envelopes](#metadata-envelopes) for more details.
707- Constraints:
708 - OPTIONAL.
709
710#### `protocol`
711
712- Same as the [`protocol`](#protocol-message-group) attribute of the
713 `messagegroup` object.
714
715#### `protocoloptions`
716
717- Type: Object
718- Description: Describes the message constraints for the protocol being used.
719 The content of this property is defined by the protocol message binding,
720 but all protocols use a common schema model for the
721 constraints defined for their metadata headers, properties or attributes.
722- Constraints:
723 - REQUIRED if `protocol` is specified.
724- Examples:
725 - See [Message protocols](#message-protocols)
726
727#### `dataschemaformat`
728
729- Type: String
730- Description: Identifies the schema format applicable to the message payload,
731 equivalent to the schema ['format'](./../../core-v1/docs/spec.md#format-attribute)
732 attribute.
733- Constraints:
734 - OPTIONAL.
735 - If present, MUST be a non-empty case-insensitive string.
736 - If present, MUST follow the naming convention `<NAME>/<VERSION>`, whereby
737 `<NAME>` is the name of the schema format and `<VERSION>` is the version of
738 the schema format in the format defined by the schema format itself.
739- Examples:
740 - 'JSONSchema/draft-07'
741 - 'Avro/1.9.0'
742 - 'Protobuf/3'
743
744#### `dataschema`
745
746- Type: Any
747- Description: Contains the inline schema for the message payload. The schema
748 format is identified by the `dataschemaformat` attribute. Equivalent to the
749 ['schema'](./../../schema-v1/docs/spec.md#221-schema) attribute.
750- Constraints:
751 - OPTIONAL.
752 - Mutually exclusive with the `dataschemauri` attribute.
753 - If present, `dataschemaformat` MUST be present.
754- Examples:
755 - See [Schema Formats](./../../schema-v1/docs/spec.md#43-schema-formats)
756
757#### `dataschemauri`
758
759- Type: URI
760- Description: Contains a relative or absolute URI that points to the schema
761 object to use for the message payload. The schema format is identified by the
762 `dataschemaformat` attribute. See
763 [Schema Formats](./../../schema-v1/docs/spec.md#43-schema-formats) for details on
764 how to reference specific schema objects for the message payload. It is not
765 sufficient for the URI to point to a schema document; it MUST resolve to a
766 concrete schema object.
767- Constraints:
768 - OPTIONAL.
769 - Mutually exclusive with the `dataschema` attribute.
770 - If present, `dataschemaformat` MUST be present.
771
772#### `dataschemaxid`
773
774- Type: XID
775- Description: Contains the `xid` of the xRegistry `schema` Resource entity
776 associated with the schema document referenced by `dataschemauri`. Note that
777 this means the entity MUST be located within the same Registry.
778- Constraints:
779 - OPTIONAL.
780 - If `dataschemauri` is also present then its value MUST be the `self`
781 URL of the entity referenced by this attribute.
782
783
784#### `datacontenttype`
785
786- Type: `String` per [RFC 2046](https://tools.ietf.org/html/rfc2046)
787- Description: Content type of the message payload. This attribute MAY be
788 duplicative with some other metadata within the message definition. For
789 example, in the case of using CloudEvents, the `envelopemetadata` attribute
790 might include the `datacontenttype` attribute. This possible duplication
791 of data is expected so as to allow for easy, more consistent discovery
792 of the message's format. This means that if this information does appear in
793 more than one location within the message metadata, all occurrences MUST
794 have the same value.
795
796 Note that when an `envelope` is defined for a message and the data of
797 interest is serialized as being nested within the envelope (e.g.
798 CloudEvents "structured" mode), then this attribute MUST be the content type
799 of the message envelope and not of the data nested within the envelope.
800
801 As specified in [RFC 2045](https://tools.ietf.org/html/rfc2045), the media
802 type part of the content type MUST be treated in a case-insensitive manner
803 by consumers, along with the attribute names in parameters. For example,
804 a `datacontenttype` of `text/plain; charset=utf-8` MUST be treated in the
805 same way as `TEXT/Plain; CharSet=utf-8`.
806- Constraints:
807 - OPTIONAL
808 - If present, MUST adhere to the format specified in
809 [RFC 2046](https://tools.ietf.org/html/rfc2046). For Media Type examples
810 see [IANA Media
811 Types](http://www.iana.org/assignments/media-types/media-types.xhtml)

813### Metadata Envelopes and Message Protocols
814
815This section defines the metadata envelopes and message protocols that are
816directly supported by this specification.
817
818Metadata envelopes lean on a protocol-neutral metadata definition like
819CloudEvents. Message protocols lean on a message model definition of a specific
820protocol like AMQP, MQTT or Kafka.
821
822A message can use either a metadata `envelope`, a message `protocol`, or both.
823
824If a message only uses a metadata `envelope`, any implicit protocol bindings
825defined by the envelope apply. For instance, a message definition that uses the
826"CloudEvents/1.0" envelope but no explicit `protocol` implicitly applies to all
827protocols for which CloudEvents bindings exist, using the respective protocol
828binding rules.
829
830If a message uses both a metadata `envelope` and a message `protocol`, the
831message binding rules take precedence over the metadata envelope rules. For
832instance, if a message definition uses the "CloudEvents/1.0" envelope and an
833"AMQP/1.0" protocol, then the implicit protocol bindings of the
834"CloudEvents/1.0" envelope are overridden by the "AMQP/1.0" protocol rules.
835
836If a message uses only a message `protocol`, only the metadata constraints
837defined by the message `protocol` rules apply.
838
839#### Property Definitions
840
841The following attributes are used to define the properties associated with
842the headers, properties or attributes defined for a message:
843
844##### `description`
845
846- Type: String
847- Description: A human-readable description of the property.
848- Constraints:
849 - OPTIONAL.
850 - If present, MUST be a non-empty string.
851
852##### `required`
853
854- Type: Boolean
855- Description: Indicates whether the property is REQUIRED to be present in a
856 message of this type.
857- Constraints:
858 - OPTIONAL.
859 - Default value MUST be `false`.
860
861##### `specurl`
862
863- Type: URI
864- Description: Contains a relative or absolute URI that points to the
865 human-readable specification of the property.
866- Constraints:
867 - OPTIONAL.
868
869##### `type`
870
871- Type: String
872- Description: The type of the property. This is used to constrain the value of
873 the property.
874- Constraints:
875 - OPTIONAL.
876 - Default value MUST be "string".
877 - The valid types are those defined in the [CloudEvents][CloudEvents Types]
878 core specification, with some additions:
879 - `any`: Any type of value, including `null`.
880 - `binary`: CloudEvents "Binary" type.
881 - `boolean`: CloudEvents "Boolean" type.
882 - `duration`: RFC3339 Duration.
883 - `integer`: CloudEvents "Integer" type (RFC 7159, Section 6).
884 - `number`: IEEE754 Double.
885 - `string`: CloudEvents "String" type.
886 - `symbol`: A `string` that is restricted to alphanumerical characters and
887 underscores.
888 - `timestamp`: CloudEvents "Timestamp" type (RFC3339 DateTime)
889 - `uri`: CloudEvents URI type (RFC3986 URI).
890 - `uritemplate`: [RFC6570][RFC6570] Level 1 URI Template.
891
892##### `value`
893
894- Type: Any
895- Description: The value of the property. With a few exceptions, see below,
896 this is the value that MUST be literally present in the message for the
897 message to be considered conformant with the message definition.
898- Constraints:
899 - OPTIONAL.
900 - If present, MUST be a valid value for the property.
901
902If the `type` property has the value `uritemplate`, `value` MAY contain
903placeholders. As defined in [RFC6570][RFC6570] (Level 1), the placeholders MUST
904be enclosed in curly braces (`{` and `}`) and each MUST be a valid `symbol`.
905Placeholders that are used multiple times in the same message definition MUST
906represent identical values.
907
908When validating a message property against this value, the placeholders act as
909wildcards. For example, the value `{foo}/bar` would match the value `abc/bar`
910or `xyz/bar`.
911
912When creating a message based on a metaschema with such a value, the
913placeholders MUST be replaced with valid values. For example, the value
914`{foo}/bar` would be replaced with `abc/bar` or `xyz/bar` when creating a
915message.
916
917If the `type` property has the value `timestamp` and the `value` property is
918set to a value of `0000-01-01T00:00:00Z`, the value MUST be replaced with the
919current timestamp when creating a message.
920
921#### Metadata Envelopes
922
923This specification only defines one metadata envelope: "CloudEvents/1.0".
924
925##### CloudEvents/1.0
926
927For the "CloudEvents/1.0" envelope, the
928[`envelopemetadata`](#envelopemetadata) object contains a property
929`attributes`, which is an object whose properties correspond to the
930CloudEvents context attributes.
931
932As with the [CloudEvents specification][CloudEvents], the attributes form a
933flat list and extension attributes are allowed. Attribute names are restricted
934to lower-case alphanumerical characters without separators.
935
936The base attributes are defined as follows:
937
938| Attribute | Type |
939| ----------------- | ------------- |
940| `specversion` | `string` |
941| `id` | `string` |
942| `type` | `string` |
943| `source` | `uritemplate` |
944| `subject` | `string` |
945| `time` | `timestamp` |
946| `dataschema` | `uritemplate` |
947| `datacontenttype` | `string` |
948
949The following rules apply to the attribute declarations:
950
951- All attribute declarations are OPTIONAL. Requirements for absent
952 definitions are implied by the CloudEvents specification.
953- The `specversion` attribute is implied by the message envelope and is
954 OPTIONAL. If present, it MUST be declared with a `string` type and set to the
955 value "1.0".
956- The `type`, `id`, and `source` attributes implicitly have the `required` flag
957 set to `true` and MUST NOT be declared as `required: false`.
958- The `id` attribute's `value` SHOULD NOT be defined.
959- The `time` attribute's `value` MUST default to `0000-01-01T00:00:00Z`
960 ("current time") and SHOULD NOT be declared with a different value.
961- The `datacontenttype` attribute's `value` is inferred from the
962 [`dataschemaformat`](#dataschemaformat) attribute of the message definition
963 if absent.
964- The `dataschema` attribute's `value` is inferred from the
965 [`dataschemauri`](#dataschemauri) attribute or
966 [`dataschema`](#dataschema) attribute of the message definition if
967 absent. If present, the value MUST match the `dataschemauri` attribute of the
968 message definition.
969- The `type` of the property definition defaults to the CloudEvents type
970 definition for the attribute, if any. The `type` of an attribute MAY be
971 modified to be further constrained. For instance, the `source` type
972 `uri` MAY be changed to `uritemplate` or the `subject` type `string` MAY be
973 constrained to a `uri` or `stringified integer`. If no CloudEvents type
974 definition exists, the default value MUST be `string`.
975
976The values of all `string` and `uritemplate`-typed attributes MAY contain
977placeholders using the [RFC6570][RFC6570] Level 1 URI Template syntax. When the
978same placeholder is used in multiple properties, the value of the placeholder
979is assumed to be identical.
980
981The following shows the format of a CloudEvents "envelopemetadata" section for
982a message (see the [model file](./model.json) for the complete definition):
983
984```yaml
985"envelope": "CloudEvents/1.0",
986"envelopemetadata" {
987 # "CloudEvents/1.0" envelope metadata
988 "specversion": {
989 "value": "1.0",
990 "type": "string"
991 },
992 "id": {
993 "value": "<STRING>", ?
994 "type": "string"
995 },
996 "type": {
997 "value": "<STRING>", ?
998 "type": "string"
999 },
1000 "source": {
1001 "value": "<STRING>", ?
1002 "type": "string"
1003 },
1004 "subject": {
1005 "value": "<STRING>", ?
1006 "type": "string"
1007 },
1008 "time": {
1009 "value": "<TIMESTAMP>", ?
1010 "type": "timestamp" ?
1011 },
1012 "dataschema": {
1013 "value": "<URITEMPLATE>", ?
1014 "type": "uritemplate" ?
1015 },
1016 "*": {
1017 "value": <ANY>, ?
1018 "type": "<TYPE>"
1019 }
1020}
1021```
1022
1023The following example declares a CloudEvent with a JSON payload. The attribute
1024`id` is REQUIRED in the declared event per the CloudEvents specification in
1025spite of such a declaration being absent here; the `type` of the `type`
1026attribute is `string` and the attribute is `required` even though the
1027declarations are absent. The `time` attribute is made `required` contrary to
1028the CloudEvents base specification. The implied CloudEvents `datacontenttype`
1029attribute value is `application/json` and the implied CloudEvents `dataschema`
1030attribute value is `https://example.com/schemas/com.example.myevent.json`:
1031
1032```yaml
1033{
1034 "envelope": "CloudEvents/1.0",
1035 "envelopemetadata": {
1036 "type": {
1037 "value": "com.example.myevent"
1038 },
1039 "source": {
1040 "value": "https://{tenant}/{module}/myevent",
1041 "type": "uritemplate"
1042 },
1043 "subject": {
1044 "type": "uri"
1045 },
1046 "time": {
1047 "required": true
1048 },
1049 },
1050 "dataschemaformat": "JsonSchema/draft-07",
1051 "dataschemauri": "https://example.com/schemas/com.example.myevent.json"
1052}
1053```
1054
1055For clarity of the definition, you MAY always declare all implied attribute
1056properties explicitly, but they MUST conform with the rules above.
1057
1058#### Message Protocols
1059
1060##### "HTTP/1.1", "HTTP/2", "HTTP/3" protocols
1061
1062The "HTTP" protocol is used to define messages that are sent over an HTTP
1063connection. The protocol is based on the
1064[HTTP Message Format][HTTP Message Format] and is common across all versions of
1065HTTP.
1066
1067The [`protocoloptions`](#protocoloptions) object MAY contain several
1068properties as defined below:
1069
1070| Property | Type | Description |
1071| --------- | ------------- | --------------------------- |
1072| `headers` | Array | The HTTP headers. See below |
1073| `query` | Map | The HTTP query parameters |
1074| `path` | `uritemplate` | The HTTP path |
1075| `method` | `string` | The HTTP method |
1076| `status` | `string` | The HTTP status code |
1077
1078HTTP allows for multiple headers with the same name. The `headers` property is
1079therefore an array of objects with `name` and `value` properties. The `name`
1080property is a string that MUST be a valid HTTP header name.
1081
1082The `query` property is a map of string keys to string values.
1083
1084The `path` property is a URI template.
1085
1086The `method` property is a string that MUST be a valid HTTP method.
1087
1088The `status` property is a string that MUST be a valid HTTP response
1089code. The `status` and `method` properties are mutually exclusive and
1090MUST NOT be present at the same time.
1091
1092The values of all `string` and `uritemplate`-typed properties and headers and
1093query elements MAY contain placeholders using the [RFC6570][RFC6570] Level 1
1094URI Template syntax. When the same placeholder is used in multiple properties,
1095the value of the placeholder is assumed to be identical.
1096
1097The following example defines a message that is sent over HTTP/1.1:
1098
1099```yaml
1100{
1101 "protocol": "HTTP",
1102 "protocoloptions": {
1103 "headers": [
1104 {
1105 "name": "Content-Type",
1106 "value": "application/json"
1107 }
1108 ],
1109 "query": [
1110 {
1111 "name": "foo",
1112 "value": "bar"
1113 }
1114 ],
1115 "path": "/foo/{bar}",
1116 "method": "POST"
1117 },
1118 "dataschemaformat": "JsonSchema/draft-07",
1119 "dataschemauri": "https://example.com/schemas/com.example.myevent.json",
1120}
1121```
1122
1123##### "AMQP/1.0" protocol
1124
1125The "AMQP/1.0" protocol is used to define messages that are sent over an
1126[AMQP][AMQP 1.0] connection. It is based on the default
1127[AMQP 1.0 Message Format][AMQP 1.0 Message Format].
1128
1129The [`protocoloptions`](#protocoloptions) object MAY contain several
1130properties, each of which corresponds to a section of the AMQP 1.0 Message,
1131as defined below:
1132
1133| Property | Type | Description |
1134| ------------------------ | ---- | ------------------------------------------------------------------------------- |
1135| `properties` | Map | The AMQP 1.0 [Message Properties][AMQP 1.0 Message Properties] section |
1136| `application-properties` | Map | The AMQP 1.0 [Application Properties][AMQP 1.0 Application Properties] section. |
1137| `message-annotations` | Map | The AMQP 1.0 [Message Annotations][AMQP 1.0 Message Annotations] section |
1138| `delivery-annotations` | Map | The AMQP 1.0 [Delivery Annotations][AMQP 1.0 Delivery Annotations] section |
1139| `header` | Map | The AMQP 1.0 [Message Header][AMQP 1.0 Message Header] section |
1140| `footer` | Map | The AMQP 1.0 [Message Footer][AMQP 1.0 Message Footer] section |
1141
1142As in AMQP, all sections and properties are OPTIONAL.
1143
1144The values of all `string`, `symbol`, `uri`, and `uritemplate`-typed properties
1145MAY contain placeholders using the [RFC6570][RFC6570] Level 1 URI Template
1146syntax. When the same placeholder is used in multiple properties, the value of
1147the placeholder is assumed to be identical.
1148
1149Example for an AMQP 1.0 message type that declares a fixed `subject` (analogous
1150to CloudEvents' `type`), a custom property, and a `content-type` of
1151`application/json` without declaring a schema reference in the message
1152definition:
1153
1154```yaml
1155{
1156 "protocol": "AMQP/1.0",
1157 "protocoloptions": {
1158 "properties": {
1159 "message-id": {
1160 "required": true
1161 },
1162 "to": {
1163 "value": "https://{host}/{queue}"
1164 },
1165 "subject": {
1166 "value": "MyMessageType",
1167 "required": true
1168 },
1169 "content-type": {
1170 "value": "application/json"
1171 },
1172 "content-encoding": {
1173 "value": "gzip"
1174 }
1175 },
1176 "application-properties": {
1177 "my-application-property": {
1178 "value": "my-application-property-value"
1179 }
1180 }
1181 }
1182}
1183```
1184
1185##### `properties` (AMQP 1.0)
1186
1187The `properties` property is an object that contains the fixed properties of
1188the AMQP 1.0 [Message Properties][AMQP 1.0 Message Properties] section. The
1189following properties are defined, with type constraints:
1190
1191| Property | Type | Description |
1192| ---------------------- | ---------------- | -------------------------------------------------------------------------------- |
1193| `message-id` | (see note below) | uniquely identifies a message within the message system |
1194| `user-id` | `binary` | identity of the user responsible for producing the message |
1195| `to` | `uritemplate` | address of the node to send the message to |
1196| `subject` | `string` | message subject |
1197| `reply-to` | `uritemplate` | address of the node to which the receiver of this message ought to send replies |
1198| `correlation-id` | `string` | client-specific id that can be used to mark or identify messages between clients |
1199| `content-type` | `symbol` | MIME content type for the message |
1200| `content-encoding` | `symbol` | MIME content encoding for the message |
1201| `absolute-expiry-time` | `timestamp` | time when this message is considered expired |
1202| `group-id` | `string` | group this message belongs to |
1203| `group-sequence` | `integer` | position of this message within its group |
1204| `reply-to-group-id` | `uritemplate` | group-id to which the receiver of this message ought to send replies to |
1205
1206The `message-id` permits the types `ulong`, `uuid`, `binary`, `string`, and
1207`uritemplate`. A `value` constraint for the `message-id` property SHOULD NOT be
1208defined in the message definition except for the case where the `message-id`
1209is a `uritemplate`.
1210
1211##### `application-properties` (AMQP 1.0)
1212
1213The `application-properties` property is a map that contains the custom
1214properties of the AMQP 1.0 [Application Properties][AMQP 1.0 Application
1215Properties] section.
1216
1217The names of the properties MUST be of type `symbol` and MUST be unique within
1218the scope of the map. The values of the properties MAY be of any permitted
1219type.
1220
1221##### `message-annotations` (AMQP 1.0)
1222
1223The `message-annotations` property is a map that contains the custom
1224properties of the AMQP 1.0 [Message Annotations][AMQP 1.0 Message Annotations]
1225section.
1226
1227The names of the properties MUST be of type `symbol` and MUST be unique within
1228the scope of the map. The values of the properties MAY be of any permitted
1229type.
1230
1231##### `delivery-annotations` (AMQP 1.0)
1232
1233The `delivery-annotations` property is a map that contains the custom
1234properties of the AMQP 1.0
1235[Delivery Annotations][AMQP 1.0 Delivery Annotations] section.
1236
1237The names of the properties MUST be of type `symbol` and MUST be unique within
1238the scope of the map. The values of the properties MAY be of any permitted
1239type.
1240
1241###### `header` (AMQP 1.0)
1242
1243The `header` property is an object that contains the properties of the
1244AMQP 1.0 [Message Header][AMQP 1.0 Message Header] section. The
1245following properties are defined, with type constraints:
1246
1247| Property | Type | Description |
1248| ---------------- | --------- | -------------------------------------------------------------- |
1249| `durable` | `boolean` | specify durability requirements |
1250| `priority` | `integer` | relative message priority |
1251| `ttl` | `integer` | message time-to-live in milliseconds |
1252| `first-acquirer` | `boolean` | indicates whether the message has not been acquired previously |
1253| `delivery-count` | `integer` | number of prior unsuccessful delivery attempts |
1254
1255###### `footer` (AMQP 1.0)
1256
1257The `footer` property is a map that contains the custom properties of the AMQP
12581.0 [Message Footer][AMQP 1.0 Message Footer] section.
1259
1260The names of the properties MUST be of type `symbol` and MUST be unique within
1261the scope of the map. The values of the properties MAY be of any permitted
1262type.
1263
1264##### "MQTT/3.1.1" and "MQTT/5.0" protocols
1265
1266The "MQTT/3.1.1" and "MQTT/5.0" protocols are used to define messages that are
1267sent over [MQTT 3.1.1][MQTT 3.1.1] or [MQTT 5.0][MQTT 5.0] connections. The
1268format describes the [MQTT PUBLISH packet][MQTT 5.0] content.
1269
1270The [`protocoloptions`](#protocoloptions) object contains the elements of the
1271MQTT PUBLISH packet directly, with the `user-properties` element corresponding
1272to the application properties collection of other protocols.
1273
1274The following properties are defined. The MQTT 3.1.1 and MQTT 5.0 columns
1275indicate whether the property is supported for the respective MQTT version.
1276
1277| Property | Type | MQTT 3.1.1 | MQTT 5.0 | Description |
1278| ------------------------- | ------------- | ---------- | -------- | -------------------------------- |
1279| `qos` | `integer` | yes | yes | Quality of Service level |
1280| `retain` | `boolean` | yes | yes | Retain flag |
1281| `topic_name` | `uritemplate` | yes | yes | Topic name |
1282| `payload_format` | `integer` | no | yes | Payload format indicator |
1283| `message_expiry_interval` | `integer` | no | yes | Message expiry interval |
1284| `response_topic` | `uritemplate` | no | yes | Response topic |
1285| `correlation_data` | `binary` | no | yes | Correlation data |
1286| `content_type` | `symbol` | no | yes | MIME content type of the payload |
1287| `user_properties` | Array | no | yes | User properties |
1288
1289Like HTTP, MQTT allows for multiple user properties with the same name,
1290so the `user_properties` property is an array of objects, each of which
1291contains a single property name and value.
1292
1293The values of all `string`, `symbol`, and `uritemplate`-typed properties and
1294user properties MAY contain placeholders using the [RFC6570][RFC6570] Level 1
1295URI Template syntax. When the same placeholder is used in multiple properties,
1296the value of the placeholder is assumed to be identical.
1297
1298The following example shows a message with the "MQTT/5.0" protocol, asking for
1299QoS 1 delivery, with a topic name of "mytopic", and a user property of
1300"my-application-property" with a value of "my-application-property-value":
1301
1302```yaml
1303{
1304 "protocol": "MQTT/5.0",
1305 "protocoloptions": {
1306 "qos": 1,
1307 "retain": false,
1308 "topic_name": "mytopic",
1309 "user_properties": [
1310 {
1311 "name": "My Application Property",
1312 "value": "Value 1"
1313 }
1314 ]
1315 }
1316}
1317```

1319##### "KAFKA" protocol
1320
1321The "KAFKA" protocol is used to define messages that are sent using the [Apache
1322Kafka][Apache Kafka] RPC protocol.
1323
1324The [`protocoloptions`](#protocoloptions) object contains the common elements
1325of the Kafka [producer][Apache Kafka producer] and
1326[consumer][Apache Kafka consumer] records, with the `headers` element
1327corresponding to the application properties collection of other protocols.
1328
1329The following properties are defined:
1330
1331| Property | Type | Description |
1332| ------------ | --------- | ------------------------------------------------------------------------- |
1333| `topic` | `string` | The topic the record will be appended to |
1334| `partition` | `integer` | The partition to which the record is to be sent or has been received from |
1335| `key` | `string` | The key that is associated with the record, UTF-8 encoded |
1336| `key_base64` | `binary` | The key that is associated with the record as a base64 encoded string |
1337| `headers` | Map | A map of headers to set on the record |
1338
1339The `key` and `key_base64` properties are mutually exclusive and MUST NOT be
1340present at the same time.
1341
1342The `partition` property is included because there are cases where applications
1343use partitions explicitly for addressing and routing messages within the scope
1344of a topic.
1345
1346The values of all `string`-, `symbol`-, and `uritemplate`-typed properties
1347and headers MAY contain placeholders using the [RFC6570][RFC6570] Level 1 URI
1348Template syntax. When the same placeholder is used in multiple properties,
1349the value of the placeholder is assumed to be identical.
1350
1351Example:
1352
1353```yaml
1354{
1355 "protocol": "Kafka",
1356 "protocoloptions": {
1357 "topic": "mytopic",
1358 "key": "thisdevice"
1359 }
1360}
1361```

1363##### "NATS" protocol
1364
1365The "NATS" protocol is used to define messages that are sent using the
1366[NATS][NATS] protocol.
1367
1368The [`protocoloptions`](#protocoloptions) object contains the available
1369elements of the NATS message for the `HPUB` operation.
1370
1371The following properties are defined:
1372
1373| Property | Type | Description |
1374| ---------- | ------------- | -------------------------------------------- |
1375| `subject` | `uritemplate` | The subject the message will be published to |
1376| `reply-to` | `uritemplate` | The subject the receiver ought to reply to |
1377| `headers` | Array | A list of headers to set on the message |
1378
1379The values of all `string`-, `symbol`-, and `uritemplate`-typed properties
1380and headers MAY contain placeholders using the [RFC6570][RFC6570] Level 1 URI
1381Template syntax. When the same placeholder is used in multiple properties,
1382the value of the placeholder is assumed to be identical.
1383
1384Example:
1385
1386```yaml
1387{
1388 "protocol": "NATS",
1389 "protocoloptions": {
1390 "subject": "mytopic",
1391 "reply-to": "replytopic"
1392 }
1393}
1394```
