38## 1. Overview
39
40A schema registry provides a repository for managing serialization, validation,
41and data type definition schemas as they are commonly used in distributed
42systems. Common schema formats include JSON Schema, JSON Structure, Apache Avro
43Schema, Google Protobuf Schema, and XML Schema. However, this specification does
44not mandate, or limit, which schema formats are used.
45
46### 1.1. Schemas
47
48Schema registries are generally used to share such schemas amongst multiple
49parties.
50
51When schemas are used to drive the serialization and encoding of data, like in
52the cases of Apache Avro or Google Protobuf, the deserialization of structured
53data from its encoded form requires the schema to be available to the
54deserializer. The compactness of these serialization formats is achieved by
55externalizing type information into a schema document. The registry allows for a
56publisher of data to publish the schema document and pass a reference to it, and
57for a consumer of data to retrieve the schema document and use it to decode the
58data.
59
60Formats like XML and JSON do not require a schema to decode the data, but
61schemas are still very useful to establish a common understanding of the data
62structures that are exchanged, provide a foundation for code generation, allow
63for validation of the data, and provide an anchor for documentation and semantic
64information, like scientific units for numeric values, that goes beyond simple
65labels and data types. Generally, it is a best practice for data structures that
66are exchanged in a distributed system to be described by a schema, even if the
67data serialization model does not require one.
68
69### 1.2. Schema References
70
71In the [CloudEvents][CloudEvents dataschema] specification, the `dataschema`
72attribute holds a URI and is specifically meant to reference a schema document
73residing in a registry. For example, a CloudEvent with a `dataschema` attribute
74pointing to a schema version in a schema registry might look like this, using
75the schema version's [`self`][xRegistry self] URL as the value of the
76`dataschema` attribute:
77
78```json
79{
80 "specversion": "1.0",
81 "id": "1234-5678-9012",
82 "type": "com.example.event",
83 "source": "https://example.com/source",
84 "dataschema": "https://example.com/registry/schemagroups/com.example.schemas/schemas/com.example.event/versions/1.0",
85 "datacontenttype": "application/vnd.google.protobuf",
86 "data_base64": "...base64-encoded-data..."
87}
88```
89
90Since this URL might be a bit long, the xRegistry core specification allows for
91an implementation to provide an alternative, shorter, self-referencing URL that
92points to the same schema version, via the [`shortself`][xRegistry shortself]
93attribute. The specification is not prescriptive about the format of the shorter
94URL, but it might follow common URL-shortening practices. With that, the above
95example might look like this:
96
97```json
98{
99 "specversion": "1.0",
100 "id": "1234-5678-9012",
101 "type": "com.example.event",
102 "source": "https://example.com/source",
103 "dataschema": "https://example.com/$267shU79S",
104 "datacontenttype": "application/vnd.google.protobuf",
105 "data_base64": "...base64-encoded-data..."
106}
107```

109### 1.3. Versioning
110
111When schemas are used in a system, they typically evolve over time. Data
112structures are extended or modified, with parts added or deprecated or even
113removed. Some of these changes are compatible with existing data, while others
114are not.
115
116Serialization generally occurs based on a specific schema version that the data
117publisher uses. Multiple versions of publishers might exist in the same system,
118using different schema versions, which is a common occurrence in systems that
119perform live updates. Once data has been published, data serialized based on
120several different versions might exist in a system, in queues, in databases, or
121in files.
122
123The schema registry therefore allows managing multiple versions of schemas,
124declares their lineage, and states their compatibility policy. The compatibility
125policy is used to determine whether a schema change is compatible with prior
126versions and whether data that has been serialized based on prior versions can
127still be deserialized and/or validated using the new schema. This compatibility
128check is important to ensure that changes to schemas do not inadvertently break
129the ability to read existing data, and MAY be enforced by implementations of the
130schema registry. The [xRegistry Core][xRegistry Core] specification defines the
131versioning and compatibility relationship mechanisms.
132
133### 1.4. Document Store
134
135The schema registry is a document store and therefore has the
136[`hasdocument`][xRegistry hasdocument] attribute defined in the xRegistry Core
137attribute (implicitly) defined as `true` for the `schema` Resource.
138
139This means that the schema registry exposes the schema document through the
140Resource's document view, using the stored media type. When no Version is
141explicitly selected, the [default version][xRegistry default-version] is
142exposed. The applicable protocol binding defines how clients select the
143document and metadata views and how those views are retrieved.
144
145This enables the ability to provide external parties with a link that they can
146use without needing to know any details about xRegistry.
147
148The applicable protocol binding also defines how clients create or update
149schema Versions through the document view.
150
151For example, the xRegistry HTTP Binding uses the `$details` URL suffix to
152access the metadata view of the schema Resource or a specific Version.
153
154Beyond this, the [xRegistry Core][xRegistry Core] specification provides rich
155filtering and export/import capabilities, which can be used to retrieve schema
156documents in bulk, or to export/import schemas and schema Versions in a
157structured way. The [xRegistry pagination][xRegistry pagination] mechanism can
158be used to retrieve large sets of schemas or schema versions in a paginated
159manner.

164

167interpreted as described in [RFC 2119](https://tools.ietf.org/html/rfc2119).
168
169For clarity, OPTIONAL attributes (specification-defined and extensions) are
170OPTIONAL for clients to use, but the servers' responsibility will vary.
171Server-unknown extension attributes MUST be silently stored in the backing
172datastore. Specification-defined and server-known extension attributes MUST
173generate an error if the corresponding feature is not supported or enabled.
174However, as with all attributes, if accepting the attribute would result in a
175bad state (such as exceeding a size limit, or results in a security issue),
176then the server MAY choose to reject the request.
177
178In the pseudo JSON format snippets `?` means the preceding attribute is
179OPTIONAL, `*` means the preceding attribute MAY appear zero or more times,
180and `+` means the preceding attribute MUST appear at least once. The presence
181of the `#` character means the remaining portion of the line is a comment.
182Whitespace characters in the JSON snippets are used for readability and are
183not normative.

185### 2.2. Terminology
186
187This specification defines the following terms:
188
189#### 2.2.1. Schema
190
191We use the term **schema** (or schema Resource) in this specification as a
192logical grouping of **schema Versions**. A **schema Version** is a concrete
193document. The **schema** Resource is a semantic umbrella formed around one or
194more concrete schema Version documents that represent iterations of the same
195logical schema. Per the definition of the [`compatibility`][xRegistry
196compatibility] attribute, all Versions of a single **schema** MUST adhere to the
197rules defined by the `compatibility` attribute. Any breaking change MUST result
198in a new **schema** Resource being created.
199
200In terms of versioning, you can think of a **schema** as a collection of
201versions that are compatible according to the selected `compatibility` mode.
202The [`deprecated`][xRegistry deprecated] attribute MAY be used to indicate the
203appropriate new schema to use following a breaking change.
204
205### 2.3. Schema Group
206
207A Schema Group is a container for schemas that are related to each other in
208some application-defined way. This specification does not impose any
209restrictions on what schemas can be contained in a Schema Group.

297## 4. Schema Registry
298
299The Schema Registry is a metadata store for organizing schemas and schema
300Versions of any kind; it is a document store.
301
302Implementations of this specification MAY include additional extension
303attributes, including the `*` attribute of type `any`.
304
305Since the Schema Registry is an application of the [xRegistry
306specification][xRegistry Core], all attributes for Groups, Resources, and
307Resource Version objects are inherited from there.
308
309### 4.1. Schema Groups
310
311The Group (`<GROUP>`) name for the Schema Registry is `schemagroup` (singular).
312The plural, used as the collection name, is `schemagroups`. The Schema Group
313does not have any specific extension attributes.
314
315A schema group is a collection of schemas that are related to each other in
316some application-defined way. A Schema Group does not impose any restrictions
317on the contained schemas, meaning that a Schema Group MAY contain schemas of
318different formats.
319
320Every schema (i.e. the schema Resource) MUST reside inside a Schema Group.
321
322Example:
323
324The following abbreviated Schema Registry content shows a single Schema Group
325containing 5 schemas.
326
327```yaml
328{
329 "specversion": "1.0-rc4",
330 # other xRegistry top-level attributes excluded for brevity
331
332 "schemagroupsurl": "http://example.com/schemagroups",
333 "schemagroupscount": 1,
334 "schemagroups": {
335 "com.example.schemas": {
336 "schemagroupid": "com.example.schemas",
337 # Other xRegistry Group-level attributes excluded for brevity
338
339 "schemasurl": "https://example.com/schemagroups/com.example.schemas/schemas",
340 "schemascount": 5
341 }
342 }
343}
344```
345
346There might be cases where all schemas within a schemagroup need to have the
347same `format` value. To enable this, set the schemagroup's `format` value to
348the string that all schemas/Versions within that schemagroup need to use.
349
350Additionally, if desired, a schemagroup-instance level constraint MAY be added:
351
352```yaml
353"constraints": {
354 "schemas.format": {
355 "default": "JsonSchema/draft-07"
356 }
357}
358```
359
360This will define a schemagroup-specific default value for the schemas' `format`
361value so clients would not need to specify it manually for each schema.
362
363### 4.2. Schema Resources
364
365The Resource (`<RESOURCE>`) inside of Schema Groups is named `schema`. The
366plural, used as the collection name, is `schemas`. Any single `schema` is a
367container for one or more `versions`, which hold the concrete schema documents
368or schema document references.
369
370All Versions of a single Schema Resource MUST adhere to the semantic rules of
371the schema's [`compatibility`][xRegistry compatibility] attribute, if specified.
372
373Implementations of this specification MAY choose to support any of the
374[`compatibility`][xRegistry compatibility] values defined in the core xRegistry
375specification.
376
377Implementations of this specification SHOULD use the xRegistry default algorithm
378for generating new `versionid` values and for determining which is the latest
379Version. See [Version IDs][xRegistry version-ids] for more information, but in
380summary it means:
381
382- `versionid`s are unsigned integers starting with `1`
383- They monotonically increase by `1` with each new Version
384- The latest is the Version with the lexically largest `versionid` value after
385 all `versionid`s have been left-padded with spaces to the same length
386
387When semantic versioning is used in a solution, it is RECOMMENDED to include a
388major version identifier in the `schemaid`, like `"com.example.event.v1"` or
389`"com.example.event.2024-02"`, so that incompatible, but historically related
390schemas can be more easily identified by users and developers. The schema
391`versionid` then functions as the semantic minor version identifier.
392
393The [`ancestorid`][xRegistry ancestorid] attribute permits multiple version
394branches to exist, and allows for implementations to determine the Version
395lineage. See the [`ancestorid`][xRegistry ancestorid] attribute in the core
396xRegistry specification for more information.
397

486#### 4.3.1. JSON Schema
487
488The [`format`](./../../core-v1/docs/spec.md#format-attribute) identifier for JSON Schema is
489`JsonSchema`.
490
491When the `format` attribute is set to `JsonSchema`, the `schema` attribute of
492the schema Resource is a JSON object representing a JSON Schema document
493conformant with the declared version.
494
495When a URI, like the Message Registry's
496[`dataschemauri`](./../../message-v1/docs/spec.md#dataschemauri), points to a JSON Schema
497document, it MAY use a [JSON pointer][JSON pointer] expression to deep link into
498the schema document to reference a particular type definition. Otherwise the
499top-level object definition of the schema is used.
500
501The version of the JSON Schema format is the version of the JSON Schema
502specification that is used to define the schema. The version of the JSON Schema
503specification is defined in the `$schema` attribute of the schema document.
504
505The identifiers for the following JSON Schema versions
506
507- Draft 07: `http://json-schema.org/draft-07/schema`
508- Draft 2019-09: `https://json-schema.org/draft/2019-09/schema`
509- Draft 2020-12: `https://json-schema.org/draft/2020-12/schema`
510
511are defined as follows:
512
513- `JsonSchema/draft-07`
514- `JsonSchema/draft/2019-09`
515- `JsonSchema/draft/2020-12`
516
517which follows the exact convention as defined for JSON schema and expecting an
518eventually released version 1.0 of the JSON Schema specification using a plain
519version number.
520
521#### 4.3.2. XML Schema
522
523The [`format`](./../../core-v1/docs/spec.md#format-attribute) identifier for XML Schema is
524`XSD`. The version of the XML Schema format is the version of the W3C XML
525Schema specification that is used to define the schema.
526
527When the `format` attribute is set to `XSD`, the `schema` attribute of the
528schema Resource is a string containing an XML Schema document conformant with
529the declared version.
530
531When a URI, like the Message Registry's
532[`dataschemauri`](./../../message-v1/docs/spec.md#dataschemauri), points to an XML Schema
533document, it MAY use an XPath expression to deep link into the schema document
534to reference a particular type definition. Otherwise the top-level object
535definition of the schema is used.
536
537The identifiers for the following XML Schema versions:
538
539- 1.0: `https://www.w3.org/TR/xmlschema-1/`
540- 1.1: `https://www.w3.org/TR/xmlschema11-1/`
541
542are defined as follows:
543
544- `XSD/1.0`
545- `XSD/1.1`
546
547#### 4.3.3. Apache Avro Schema
548
549The [`format`](./../../core-v1/docs/spec.md#format-attribute) identifier for Apache Avro
550Schema is `Avro`. The version of the Apache Avro Schema format is the version
551of the Apache Avro Schema release that is used to define the schema.
552
553When the `format` attribute is set to `Avro`, the `schema` attribute of the
554schema Resource is a JSON object representing an Avro schema document conformant
555with the declared version.
556
557Examples:
558
559- `Avro/1.8.2` is the identifier for the Apache Avro release 1.8.2.
560- `Avro/1.11.0` is the identifier for the Apache Avro release 1.11.0
561
562When a URI, like the Message Registry's
563[`dataschemauri`](./../../message-v1/docs/spec.md#dataschemauri), points to an Avro Schema
564document, it MAY use a URI fragment suffix `[:]{record-name}` to deep link into
565the schema document to reference a particular type definition. Otherwise the
566top-level object definition of the schema is used. The ':' character is used as
567a separator when the URI already contains a fragment.
568
569Examples:
570
571- If the Avro schema document is referenced using the URI
572`https://example.com/avro/telemetry.avsc#TelemetryEvent`, the URI fragment
573`#TelemetryEvent` references the record declaration of the `TelemetryEvent`
574record.
575- If the Avro schema document is a local Schema Registry reference like
576`#/schemagroups/com.example.telemetry/schemas/com.example.telemetrydata`, in
577which the reference is already in the form of a URI fragment, the suffix is
578appended, separated by a colon, for instance
579`.../com.example.telemetrydata:TelemetryEvent`.
580
581#### 4.3.4. Protobuf Schema
582
583The [`format`](./../../core-v1/docs/spec.md#format-attribute) identifier for Protobuf Schema
584is `Protobuf`. The version of the Protobuf Schema format is the version of the
585Protobuf syntax that is used to define the schema.
586
587When the `format` attribute is set to `Protobuf`, the `schema` attribute of the
588schema Resource is a string containing a Protobuf schema document conformant
589with the declared version.
590
591- `Protobuf/3` is the identifier for the Protobuf syntax version 3.
592- `Protobuf/2` is the identifier for the Protobuf syntax version 2.
593
594A URI, like the Message Registry's
595[`dataschemauri`](./../../message-v1/docs/spec.md#dataschemauri), that points to a Protobuf
596Schema document MUST reference a Protobuf `message` declaration contained in the
597schema document using a URI fragment suffix `[:]{message-name}`. The ':'
598character is used as a separator when the URI already contains a fragment.
599
600Examples:
601
602- If the Protobuf schema document is referenced using the URI
603 `https://example.com/protobuf/telemetry.proto`, the URI fragment
604 `#TelemetryEvent` references the message declaration of the `TelemetryEvent`
605 message.
606- If the Protobuf schema document is a local Schema Registry reference like
607 `#/schemagroups/com.example.telemetry/schemas/com.example.telemetrydata`, in
608 which the reference is already in the form of a URI fragment, the suffix
609 is appended, separated by a colon, for instance
610 `.../com.example.telemetrydata:TelemetryEvent`.
611
612#### 4.3.5. JSON Structure Schema
613
614The [`format`](./../../core-v1/docs/spec.md#format-attribute) identifier for JSON Structure
615Schema is `JsonStructure`. When the `format` attribute is set to `JsonStructure`,
616the `schema` attribute of the schema Resource is a JSON object representing a JSON
617Structure schema document [JSTRUCT-CORE].
618
619The version identifier follows the pattern `JsonStructure/{version}`, where
620`{version}` is the version of the JSON Structure Core specification that is
621used to define the schema.
622
623`JsonStructure/draft-04` is the identifier for the Internet-Draft version 04 of
624the JSON Structure Core specification. If a future RFC is published, the
625version identifier will be updated to reflect the RFC number, for example
626`JsonStructure/rfc-0000`.
627
628When a URI, like the Message Registry's
629[`dataschemauri`](./../../message-v1/docs/spec.md#dataschemauri), points to a JSON Structure
630schema document, it MAY use a [JSON pointer][JSON pointer] expression to deep
631link into the schema document to reference a particular type definition. This is
632typically used to reference type definitions within the `definitions` namespace.
633
634Examples:
635
636- `https://example.com/schemas/person.json#/definitions/Employee` uses the
637 `#/definitions/Employee` fragment to reference the `Employee` type definition.
638- For local Schema Registry references like
639 `#/schemagroups/com.example.schemas/schemas/com.example.person/versions/1/definitions/Employee`,
640 append the JSON Pointer fragment to reference a specific type within that schema.

643
644Like the [xRegistry Core][xRegistry Core] specification, this specification does
645not explicitly address authentication or authorization levels of users, nor how
646to securely protect the APIs.
647
648It is expected that any implementation of this specification will use
649authentication and authorization mechanisms that are appropriate for the
650application domain and the deployment environment. This MAY include, but is not
651limited to, OAuth 2.0, OpenID Connect, API keys, or other mechanisms appropriate
652for the use case.
653
654For authorization, the `schemagroup` concept provides a natural authorization
655boundary, where users can be granted access to specific schema groups, and
656therefore to the schemas contained within those groups. The `schema` Resource
657itself can be used to further restrict access to specific schema Versions within
658a schema, allowing for fine-grained access control.
