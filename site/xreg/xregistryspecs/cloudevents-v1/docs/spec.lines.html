20## Overview
21
22The "CloudEvents Registry" is a universal catalog and discovery metadata format,
23as well as a metadata service API for messaging and eventing schemas,
24metaschemas, and messaging and eventing endpoints.
25
26The registry is a composite xRegistry model that combines the [Schema
27Registry](./../../schema-v1/docs/spec.md), the [Message Definitions
28Registry](./../../message-v1/docs/spec.md), and the [Endpoint Registry](./../../endpoint-v1/docs/spec.md)
29into a single, unified metadata model. This model can be used to describe
30messaging and eventing endpoints, their messages, and the schemas of the
31messages' payloads in a single metadata document or via an API.
32
33As such, this specification builds upon all those specifications for its
34definitions and demonstrates how they can be used together in a single metadata
35model.
36
37The name "CloudEvents Registry" indicates that the registry is primarily
38motivated by the development of CloudEvents-based event flows, but it is not
39limited to CloudEvents. It can be used to describe any asynchronous messaging or
40eventing endpoint and its messages, including endpoints that do not use
41CloudEvents at all. The [Message
42Formats](./../../message-v1/docs/spec.md#metadata-envelopes-and-message-protocols) section
43therefore describes not only the attribute meta-schema for CloudEvents, but also
44meta-schemas for the native message envelopes of MQTT, AMQP, and other messaging
45protocols.

49### Notational Conventions
50
51The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
52"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
53interpreted as described in [RFC 2119](https://tools.ietf.org/html/rfc2119).
54
55For clarity, OPTIONAL attributes (specification-defined and extensions) are
56OPTIONAL for clients to use, but the servers' responsibility will vary.
57Server-unknown extension attributes MUST be silently stored in the backing
58datastore. Specification-defined attributes and server-known extension
59attributes MUST generate an error if the corresponding feature is not supported
60or enabled. However, as with all attributes, if accepting the attribute results
61in a bad state (such as exceeding a size limit or resulting in a security
62issue), then the server MAY choose to reject the request.
63
64In the pseudo JSON format snippets `?` means the preceding attribute is
65OPTIONAL, `*` means the preceding attribute MAY appear zero or more times,
66and `+` means the preceding attribute MUST appear at least once. The presence
67of the `#` character means the remaining portion of the line is a comment.
68Whitespace characters in the JSON snippets are used for readability and are
69not normative.

71## CloudEvents Registry
72
73The CloudEvents Registry is a universal catalog and discovery metadata format
74as well as a metadata service API for messaging and eventing schemas,
75metaschemas, and messaging and eventing endpoints.
76
77The CloudEvents registry model contains three separate registries that can be
78implemented separately or in combination.
79
80- The [Schema Registry](./../../schema-v1/docs/spec.md) specification describes the metadata
81 description of payload schemas for events and messages. The schema registry
82 is universally applicable to any scenario where collaborating parties share
83 structured data that is defined by formal schemas. For instance, when storing
84 Protobuf encoded structured data in a cloud file store, you might place a
85 schema registry in file form in the parent directory, which formally
86 organizes and documents all versions of all Protobuf schemas that are used
87 in the directory.
88- The [Message Definitions Registry](./../../message-v1/docs/spec.md) specification
89 describes the metadata description of events and messages. The payload
90 schemas for events and messages can be embedded in the definition, reference
91 an external schema document, or can be referenced into the schema registry.
92 The message definitions registry is universally applicable to any
93 asynchronous messaging and eventing scenario. You might define a group of
94 definitions that describe precisely which messages, with which metadata, are
95 permitted to flow into a channel and can thus be expected by consumers of
96 that channel and then associate that definition group with a topic or queue
97 in your eventing or messaging infrastructure. That association might be a
98 metadata attribute on the topic or queue in the messaging infrastructure
99 that embeds the metadata or points to it.
100- The [Endpoint Registry](./../../endpoint-v1/docs/spec.md) specification defines the
101 metadata description of network endpoints that accept or emit events and
102 messages. The endpoint registry is a formal description of associations of
103 message definitions and network endpoints, which can be used to discover
104 endpoints that consume or emit particular messages or events via a central
105 registry. The message definitions can be embedded into the endpoint metadata
106 or as a reference into the message definitions registry.
107
108The metadata model is structured such that network endpoint information and
109message metadata and payload schemas can be described compactly in a single
110metadata object (and therefore as a single document) in the simplest case or
111can be spread out and managed across separate registry products in a
112sophisticated large-enterprise scenario.
113

421While the CloudEvents Registry is primarily motivated by enabling development
422of CloudEvents-based event flows, the registry is not limited to CloudEvents.
423It can be used to describe any asynchronous messaging or eventing endpoint and
424its messages, including endpoints that do not use CloudEvents at all. The
425[Message
426Formats](./../../message-v1/docs/spec.md#metadata-envelopes-and-message-protocols) section
427therefore not only describes the attribute meta-schema for CloudEvents, but
428also meta-schemas for the native message envelopes of MQTT, AMQP, and other
429messaging protocols.
430
431The registry is designed to be extensible to support any structured data
432encoding and related schemas for message or event payloads. The [Schema
433Formats](./../../schema-v1/docs/spec.md#43-schema-formats) section describes the meta-schema
434for JSON Schema, XML Schema, Apache Avro schema, and Protobuf schema.

436### File format
437
438A CloudEvents Registry can be implemented using the Registry API or with plain
439text files.
440
441When using the file-based model, files with the extension `.cereg` use JSON
442encoding. Files with the extension `.cereg.yaml` or `.cereg.yml` use YAML
443encoding. The formal JSON schema for the file format is defined in the
444[CloudEvents Registry Document
445Schema](./../schemas/document-schema.json),
446which implements the Registry format and the CloudEvents Registry format.
447
448The media-type for the file format is `application/cloudevents-registry+json`
449for the JSON encoding and `application/cloudevents-registry+yaml` for the YAML
450encoding.
451
452The JSON schema identifier is `https://cloudevents.io/schemas/registry` and the
453`specversion` property indicates the version of this specification that the
454elements of the file conform to.
455
456A CloudEvents Registry file MUST contain a single JSON object or YAML document.
457The object declares the roots of the three sub-registries, which are either
458embedded or referenced. Any of the three sub-registries MAY be omitted.
459
460```yaml
461{
462 "$schema": "https://cloudevents.io/schemas/registry",
463 "specversion": "1.0-rc4",
464 "registryid": "STRING",
465
466 "endpointsurl": "URL",
467 "endpointscount": INT,
468 "endpoints": { ... },
469
470 "messagegroupsurl": "URL",
471 "messagegroupscount": INT,
472 "messagegroups": { ... },
473
474 "schemagroupsurl": "URL",
475 "schemagroupscount": INT,
476 "schemagroups": { ... }
477}
478```
479
480While the file structure leads with endpoints followed by definition groups and
481then schema groups by convention, the order of the sub-registries is not
482significant.
