1# Pagination - Version 0.1-wip
2
3This document describes a mechanism by which a server can return a set of
4records to a client in an incremental fashion. Often this will be used when
5a client is doing a query for a set of records and the result set is too large
6to return in one response.
7
8## Notations and Terminology
9
10### Notational Conventions
11
12The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
13"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
14interpreted as described in [RFC2119](https://tools.ietf.org/html/rfc2119).
15
16## Client Request
17
18When a client sends a request to a server which is meant to result in a
19set of records being returned, the client MAY include extra attributes
20to control how those records are to be returned if the results can not
21fit within one response message.
22
23### Client Attributes
24
25The following list of attributes MAY be included in a client's request for
26a set of records from a server. The client MUST only specify these on
27the initial request for the set. If the results can not fit within one
28response then these attributes MUST NOT be added to subsequent requests
29by the client. Note that the server MAY include these attributes within
30the URI-reference returned in a response message, but the client MUST NOT
31modify those values.
32
33#### limit
34
35- Type: `Unsigned 64-bit Integer`
36- Description: Indicates the maximum number of records per message
37 that the client is willing to accept. If the server is unable to
38 meet this criterion then it MUST generate an error.
39 There is no default value for this attribute.
40 If this attribute is not specified, then the server MAY choose to send back
41 as many or as few records per response message.
42- Constraints:
43 - OPTIONAL.
44 - MUST be an unsigned 64-bit integer with a value greater than 0.
45- Examples:
46 - `100`
47
48## Server Response
49
50When a server returns a subset of records, it MAY include additional attributes
51to help the client retrieve the next subset of records.
52
53### Server Attributes
54
55The following list of attributes MAY be included in a server's response to
56a client's request for a set of records.
57
58Note: in the examples listed below, the use of certain query parameters
59in the response messages from the server, such as `offset` and `limit`,
60are an implementation detail of the server. How the server encodes the
61information it needs to retrieve a certain subset of records is not mandated by
62this specification.
63
64#### link
65
66- Type: `URI-Reference`
67- Description: A URI-Reference to another subset of records. The relationship
68 of the next subset to the current subset MUST be specified by the `rel`
69 attribute. This value is meant to be treated as an opaque value by the
70 client. If a client uses this value in a subsequent request then it
71 MUST use it as it was provided by the server. Any attempt to modify its
72 value, or attributes (such as query parameters), is not defined by this
73 specification and the results from the server are undefined.
74- Constraints:
75 - MUST NOT be present if there are no more records for the `rel` type of
76 relationship.
77 - MUST be present if there are more records for the `rel` type of
78 relationship.
79 - MUST be a URI-Reference as defined in
80 [RFC3986](https://tools.ietf.org/html/rfc3986).
81- Examples:
82 - `http://example.com/people?offset=3&limit=100`
83 - `http://example.com/people?id=1234`
84 - `http://example.com/people?resultset=7a835`
85
86#### rel
87
88- Type: `String`
89- Description: A string representing the relationship between the records
90 available via the `link` URI-Reference and the current subset of records.
91 This attribute adheres to the Relation Type as defined in section 5.3
92 of [RFC5988](https://tools.ietf.org/html/rfc5988).
93 This specification uses the following values as defined by section 6.2.2
94 in [RFC5988](https://tools.ietf.org/html/rfc5988):
95 - `next` - indicates the next subset of records in the sequence of records
96 being returned.
97 - `prev` - indicates the previous subset of records in the sequence of
98 records being returned.
99 - `first` - indicates the first subset of records in the sequence of records
100 being returned.
101 - `last` - indicates the last subset of records in the sequence of records
102 being returned.
103 Unless otherwise constrained by a specification leveraging this
104 specification, additional values MAY be defined.
105- Constraints:
106 - REQUIRED if the `link` attribute is present.
107 - MUST be a string as defined by `relation-types` in
108 [RFC5988](https://tools.ietf.org/html/rfc5988).
109
110#### expires
111
112- Type: `Timestamp`
113- Description: Indicates when the complete set of records referenced by the
114 `link` will no longer be available. When not specified, the availability
115 of the data is undefined by this specification. However, it is RECOMMENDED
116 that this attribute only be excluded when the data being iterated over
117 is not expected to change very often and therefore the server will
118 typically not need to save any state related to this client's requests.
119- Constraints:
120 - OPTIONAL.
121
122#### count
123
124- Type: `Unsigned 64-bit Integer`
125- Description: Indicates the total number of records in the complete set
126 referenced by the `link`. Note that this is not the number of records in any one
127 message, but instead it is the aggregate count of records across all
128 messages in the set.
129- Constraints:
130 - STRONGLY RECOMMENDED.
131 - MUST be an unsigned integer.
132 - MUST be consistent across all `link` attributes and messages for a
133 particular set of records.
134
135## HTTP Binding
136
137The following describes how the attributes defined above would appear in a
138flow of HTTP messages during the retrieval of a set of records.
139
140### Request for a record set
141
142To request a set of records from a server, a client will send an HTTP GET
143request to the server. How this URL is determined is out of scope of this
144specification.
145
146The client MAY include the `limit` attribute as part of this request. Unless
147there is some out-of-band negotiation to determine a different mechanism,
148the server MUST accept the `limit` attribute as a query parameter (named
149`limit`, case sensitive) in the URL.
150
151For example:
152```
153http://example.com/people?limit=100
154```
155
156### Response for a record set
157
158Each successful response from the server MUST adhere to the following:
159- MUST respond with an HTTP 200.
160- MUST include zero or more records.
161- If the response refers to the start of the set of records, then the `prev`
162 Link MUST NOT be included in the response.
163- If the response does not include the start of the set of records, then the
164 `prev` Link MAY be included in the response.
165- The response MAY include the `first` Link in any response.
166- If the `limit` attribute was specified as part of the flow, the response MUST
167 NOT include more records than what the `limit` attribute has indicated.
168- If the response refers to the end of the set of records, then the `next`
169 Link MUST NOT be included in the response.
170- If the response does not refer to the end of the set of records, then the
171 `next` Link MUST be included in the response.
172- The response MAY include the `last` Link in any response.
173- The response MAY include the `expires` attribute in any response as an
174 HTTP "Expires" header. If present, it MUST adhere to the format specified in
175 [RFC3339](https://tools.ietf.org/html/rfc7234#section-5.3).
176- It is STRONGLY RECOMMENDED that all responses include the `count` attribute.
177
178Additionally, Links MUST appear in the HTTP response as HTTP headers using
179the format described in [RFC5988](https://tools.ietf.org/html/rfc5988).
180
181Example 1:
182```
183Link: <http://example.com?limit=100&offset=3>;rel=next
184Link: <http://example.com?limit=100&offset=1>;rel=prev
185```
186
187Example 2:
188```
189Link: <http://example.com?resultset=83d71>;rel=next
190Expires: Thu, 01 Dec 2021 16:00:00 GMT
191```
192
193Example 3:
194```
195Link: <http://example.com?id=1001>;rel=next;count=3000
196Link: <http://example.com?id=0>;rel=prev;count=3000
197```
198
199### Iterating over the record set
200
201Once the record set retrieval has started, the client MAY use the Links
202returned from the server to iterate through the full set of records.
203Typically, the client will use the `next` Link from each response to retrieve
204the next subset of records until a response is returned without a `next` Link -
205indicating that it has reached the end.
206
207However, if other Links are provided by the server, then the client MAY
208use those Links instead to follow a different traversal path through the
209records.
