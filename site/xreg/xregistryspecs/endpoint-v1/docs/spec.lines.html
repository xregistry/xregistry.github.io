7## Abstract
8
9This specification defines an endpoint registry extension to the xRegistry
10document format and API [specification](./../../core-v1/docs/spec.md). An endpoint registry
11allows for publishing and discovery of asynchronous event sources, sinks, and
12subscription points in the scope of a system, along with important
13configuration parameters.

24## Overview
25
26This specification defines a registry of metadata definitions for abstract and
27concrete network endpoints to which messages can be produced, from which
28messages can be consumed, or which make messages available for subscriptions.
29
30The metadata model defined in this specification is specifically focused on
31describing unidirectional endpoints for asynchronous information flows like
32discrete events, event streams, queueing, and publish/subscribe patterns.
33
34Endpoint information is provided through the registry for discovery of
35endpoints, dynamic configuration of clients, and code generation.
36
37The model allows for a loose correlation of endpoints through a `channel`
38concept, to designate, for instance, the input and output ends of a queue, but
39it intentionally avoids being specific about the shape of messaging and
40eventing entities. The correlation of endpoints for the purposes of realizing
41specific message exchange patterns like request/response or scatter/gather is
42also intentionally out of scope for this metadata model, because modeling such
43correlation contracts with sufficient depth is a whole additional definition
44layer above what this model aims to achieve.
45
46The goal of this endpoint metadata model is to provide metadata structure to
47asynchronous topics and streams and queues in a way that is similar to how
48table and column definitions provide structure to databases. Database schemas
49structure data that you have. Endpoint definitions with their referenced or
50embedded message definitions with referenced or embedded schema definitions
51structure data that you will yet receive.
52
53Continuing that analogy, the endpoint scope corresponds to the database, the
54message groups are schema scopes, and the message definitions correspond to
55tables. The schema associated with a message definition determines the column
56layout of the table. As event streams often end up landing in databases for
57long-term archival and analysis, this structural alignment is very helpful.
58
59### Endpoints
60
61In a distributed system, the networked input sinks and output sources of an
62application, or an application infrastructure component like an event broker,
63are commonly called “endpoints”. Those endpoints serve as communication
64conduits to make information available to the application, or for the
65application to make information available to others.
66
67In this specification we distinguish three distinct `usage` roles for
68endpoints:
69
70- `producer`: A producer endpoint is made available by a consumer or
71 intermediary (like an application or a queue) to a producer, so that the
72 producer can send events/messages to the endpoint. Those events/messages
73 MUST conform to the declared constraints. If the endpoint is associated with
74 at least one message group, only messages/events that match one of the
75 declared message definitions can be sent. If the message definition
76 references a data schema, the message payload MUST match that schema.
77
78- `consumer`: A consumer endpoint is made available by a producer or
79 intermediary for a consumer to retrieve messages/events from. Examples for
80 these are queues or consumer groups on streams, but also peer-to-peer
81 endpoints exposed by applications.
82
83- `subscriber`: A subscriber endpoint is made available to consumers for the
84 purpose of setting up their own consumer endpoint. The
85 [CloudEvents Subscriptions API](https://github.com/cloudevents/spec/blob/main/subscriptions/spec.md)
86 specification enumerates the subscription mechanisms intended for these
87 endpoints. As subscription mechanisms can vary substantially across products
88 that implement the same protocol, it is RECOMMENDED to use the `label`
89 mechanism to identify the specific product that provides the endpoint.
90
91Each endpoint definition defines a `protocol` selector by which the specific
92network application protocol is chosen to communicate with the endpoint. If a
93networked entity supports multiple protocols, each protocol endpoint MUST be
94declared separately, even if those are multiplexed over the same port. For
95instance, if you have an MQTT broker that can dynamically select between
96MQTT 3.1.1 and MQTT 5.0, those endpoints are to be declared separately as
97the capabilities differ substantially.
98
99The `protocol` selector value determines which `protocoloptions` become
100available to define for the endpoint. The protocol-specific options are
101enumerated and explained in [protocol options](#protocol-options).
102
103Each endpoint MAY also define an `envelope` selector which allows for defining
104particular `envelopeoptions` at the endpoint level. For CloudEvents, this
105permits the definition of the serialization mode (binary or structured) and the
106event format for structured mode.
107
108### Message Groups
109
110The Endpoint is an xRegistry group-level construct that is conceptually an
111extension of the [message definition group](./../../message-v1/docs/spec.md), meaning there
112are no “groups of endpoints”. An endpoint MAY contain directly embedded
113message definitions. In the simplest case, an endpoint MAY embed its message
114definitions locally which in turn MAY embed their data schema definitions
115locally, all in one compact construct.
116
117More commonly, Endpoints will reference one or more
118[message definition groups](./../../message-v1/docs/spec.md) that are defined externally in
119a message registry, and which have the advantage of being shareable across
120multiple Endpoints.
121
122For describing a message broker queue, the best approach is to define a
123message group that defines the messages that are allowed to flow on the
124queue and for that message group to then be referenced from the `producer` and
125the `consumer` endpoints of the queue, whereby both of those endpoints share
126the same `channel` identifier.
127
128In the endpoint context, message groups have a function similar to interfaces
129in programming languages. They define related sets of messages that can be
130associated with an endpoint all at once.
131
132### Scenarios
133
134Endpoint definitions can be abstract or concrete, distinguished by the
135`deployed` flag. If the `deployed` flag is set to `true`, one can expect the
136endpoint to be reachable on the network with the given parameters, assuming
137the client is within the same network scope. If the flag is set to `false`,
138the endpoint definition is to be treated like a template where configuration
139elements like the endpoint URI will have to be supplied by external
140configuration for the client to become functional.
141
142The latter can be used for Endpoint definitions that define endpoint patterns
143common in applications of the MQTT protocol.
144For instance, the [Eclipse Sparkplug](https://sparkplug.eclipse.org/) protocol
145is a convention that defines endpoint roles and messages and schemas for MQTT,
146and the
147[SparkPlugB](./../../cloudevents-v1/samples/mqtt-sparkplugB.xreg.json)
148example illustrates how Registry Endpoints can model the convention in
149formal terms.

153### Notational Conventions
154
155The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
156"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
157interpreted as described in [RFC 2119](https://tools.ietf.org/html/rfc2119).
158
159For clarity, OPTIONAL attributes (specification-defined and extensions) are
160OPTIONAL for clients to use, but the servers' responsibility will vary.
161Server-unknown extension attributes MUST be silently stored in the backing
162datastore. Specification-defined attributes and server-known extension
163attributes MUST generate an error if the corresponding feature is not supported
164or enabled. However, as with all attributes, if accepting the attribute results
165in a bad state (such as exceeding a size limit or resulting in a security
166issue), then the server MAY choose to reject the request.
167
168In the pseudo JSON format snippets `?` means the preceding attribute is
169OPTIONAL, `*` means the preceding attribute MAY appear zero or more times,
170and `+` means the preceding attribute MUST appear at least once. The presence
171of the `#` character means the remaining portion of the line is a comment.
172Whitespace characters in the JSON snippets are used for readability and are
173not normative.

185## Endpoint Registry Model
186
187The Endpoint Registry is a registry of metadata definitions for abstract and
188concrete network endpoints to which messages can be produced, from which
189messages can be consumed, or which make messages available via subscription
190and delivery to a consumer-designated endpoint.
191
192As discussed in the [CloudEvents Registry overview](./../../cloudevents-v1/docs/spec.md),
193endpoints are supersets of
194[message definition groups](./../../message-v1/docs/spec.md#message-definition-groups) and
195MAY contain inlined messages. Therefore, the Resources in the meta-model for
196the Endpoint Registry are likewise `messages` as defined in the
197[message catalog specification](./../../message-v1/docs/spec.md).
198
199The formal xRegistry extension model of the Endpoints Registry
200resides in the [model.json](./model.json) file.
201

357### Endpoints Groups
358
359The Group plural name (`<GROUPS>`) is `endpoints`, and the Group singular
360name (`<GROUP>`) is `endpoint`.
361
362The following attributes are defined for the `endpoint` object in addition
363to the xRegistry-defined core
364[attributes](./../../core-v1/docs/spec.md#attributes-and-extensions):
365
366#### `usage`
367
368- Type: Array of String (Enum: `subscriber`, `consumer`, `producer`)
369- Description: The `usage` attribute is a set of strings that indicates the
370 intended usage of the endpoint by communicating parties. In other words, the
371 roles a client can act in when talking with the endpoint.
372
373 Each of these parties will have a different perspective on an endpoint. For
374 instance, a `producer` endpoint is seen as a "target" by the originator of
375 messages, and as a "source" by the party that accepts the messages. The
376 nomenclature used for the `usage` field is primarily oriented around the
377 common scenario of network endpoints being provided by some sort of
378 intermediary like a message broker. The term `producer` primarily describes
379 the relationship of a client with that intermediary.
380
381 In a direct-delivery scenario where the originator of messages connects
382 directly to the target (e.g. a "WebHook" call), the target endpoint
383 implements the accepting end of the `producer` relationship.
384
385 Some of these perspectives are mentioned below for illustration, but not
386 formally defined or reflected in the metadata model. Perspectives depend on
387 the context in which the endpoint metadata is used and this metadata model is
388 intentionally leaving perspectives open to users.
389
390 The following values are defined for `usage`
391
392 - `subscriber`: The endpoint offers management of subscriptions that cause
393 messages to be delivered to some other endpoint. A `subscriber` endpoint
394 is a control-plane endpoint: it does not itself transfer messages.
395 Establishing subscription interest is the only interaction it describes.
396
397 Depending on the protocol, subscription interest is established by the
398 [CloudEvents Subscriptions API][CloudEvents Subscriptions API], an MQTT
399 `SUBSCRIBE` packet, establishment of an AMQP link with the endpoint node
400 as source, creation of a Kafka consumer group, or a NATS subscription.
401
402 Some perspectives that might exist on a subscriber endpoint:
403 - Application from which messages originate.
404 - Application which accepts messages from the delivery agent.
405 - Application which manages subscriptions for delivery of messages to the
406 target application. This might be a message broker subscription manager.
407
408 - `consumer`: The endpoint offers messages being consumed (pulled) from it.
409
410 Some perspectives that might exist on a consumer endpoint:
411 - Message store or source which makes messages available for consumption;
412 this might be a message broker topic or a queue.
413 - Proxy or other intermediary which solicits messages from the source and
414 forwards them to the target endpoint.
415 - Application which consumes messages.
416
417 - `producer`: The endpoint offers messages being produced (pushed) to it.
418
419 Some perspectives might exist on a producer endpoint:
420 - Application from which messages originate.
421 - Reverse proxy or other intermediary which accepts messages from the
422 originator and forwards them to the target endpoint.
423 - Application which accepts messages. This might be a message broker topic
424 or a queue. This might be an HTTP endpoint that directly accepts and
425 handles messages.
426
427 Any endpoint can be seen from different role perspectives:
428
429 There might also be further perspectives such as pipeline stages for
430 pre-/post-processing, etc.
431
432- Constraints:
433 - REQUIRED.
434 - MUST contain only the following possible values:
435 - "subscriber"
436 - "consumer"
437 - "producer"
438 - MUST be an array of at least one value.
439 - MUST declare exactly one usage value, except for the single combination
440 permitted below.
441 - MUST NOT combine `producer` with any other value.
442 - MUST NOT declare all three values.
443 - MAY declare `["subscriber", "consumer"]` only when the protocol is
444 `MQTT/3.1.1`, `MQTT/5.0`, `AMQP/1.0`, or `NATS`. In these protocols a
445 single client connection both establishes subscription interest and
446 receives the resulting messages, so the two roles are served by one
447 protocol interface and one endpoint contract.
448 - MUST NOT declare `["subscriber", "consumer"]` for `HTTP` or `KAFKA`
449 endpoints. In those protocols the two roles are distinct interfaces and
450 MUST be modeled as separate Endpoint resources.
451 - Endpoints that jointly describe more than one role SHOULD be declared
452 separately and correlated with a shared `channel` value.
453
454#### `channel`
455
456- Type: String
457- Description: A string that can be used to correlate Endpoints. Any Endpoints
458 within an instance of an Endpoint Registry that share the same non-empty
459 `channel` value MUST have some relationship. This specification does not
460 define that relationship or the specific values used in this property.
461 However, it is expected that the `usage` value in combination with this
462 `channel` property will provide some information to help determine the
463 relationship.
464
465 For instance, a message broker queue "queue1" might be represented with a
466 `producer` endpoint and a `consumer` endpoint, both with the same `channel`
467 attribute value of "queue1".
468
469 An event processing pipeline might have a sequence of stages, each with a
470 `producer` endpoint and a `consumer` endpoint, all with the same `channel`
471 attribute value of "pipeline1", or some further qualification like
472 "pipeline1-stage1", etc.
473
474 This specification does not make any statement about whether two endpoints
475 that do not share the same non-empty value have any relationship or not.
476 They might, but how this is determined is out of scope of this specification.
477 Additionally, while it is expected that this attribute's value will be a
478 single value, given this specification does not place any constraints on
479 its syntax or semantic meaning, implementations might choose to "encode"
480 multiple values within this single string. That would then imply that the
481 comparison algorithm of two `channel` values might need to be more
482 complicated than a "string compare" in those cases.
483
484- Constraints:
485 - OPTIONAL.
486 - When specified, the value MUST be a non-empty string.
487- Examples:
488 - `queue1`
489
490#### `envelope`
491
492- Type: String
493- Description: The name of the specification that defines the Resource
494 stored in the registry. Often it is difficult to unambiguously determine
495 what a Resource is by simply inspecting its serialized form. This attribute
496 provides a mechanism by which it can be determined without examination of
497 the Resource at all.
498- Constraints:
499 - MUST be a non-empty case-insensitive string of the form
500 `<SPEC>[/<VERSION>]`,
501 where `<SPEC>` is the non-empty string name of the specification that
502 defines the Resource. An OPTIONAL `<VERSION>` value SHOULD be included if
503 there are multiple versions of the specification available.
504 - If a `<VERSION>` is specified at the Group level, all Resources within that
505 Group MUST have a `<VERSION>` value that is at least as precise as its
506 Group, and MUST NOT expand it. For example, if a Group had a
507 `envelope` value of `myspec`, then Resources within that Group can have
508 `envelope` values of `myspec` or `myspec/1.0`. However, if a Group has a
509 value of `myspec/1.0`, it would be invalid for a Resource to have a value
510 of `myspec/2.0` or just `myspec`. Additionally, if a Group does not have an
511 `envelope` attribute, then there are no constraints on its Resources'
512 `envelope` attributes.
513 - This specification places no restriction on the syntax of the
514 `<VERSION>` value.
515- Examples:
516 - `CloudEvents/1.0`
517
518#### `envelopeoptions`
519
520- Type: Map
521- Description: Configuration details of the endpoint with respect to the
522 envelope format used to transmit the messages.
523
524- Constraints:
525 - OPTIONAL.
526- Examples:
527 - For an endpoint using an `envelope` value of `CloudEvents/1.0`:
528 `{ "mode": "binary", "format": "application/json" }`
529
530This specification defines the following envelope options for the indicated
531`envelope` values:
532
533##### `CloudEvents/1.0`
534
535- `mode` : indicates whether the CloudEvent will use `binary` or `structured`
536 [mode](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md#message).
537 When specified, its value MUST be one of: `binary` or `structured`, case
538 sensitive. When not specified, the endpoint is indicating that either mode
539 is acceptable.
540- `format` : indicates the format of the CloudEvent when sent in `structured`
541 mode. This attribute MUST NOT be specified when `mode` is `binary`. The value
542 used MUST match the expected content type of the message (e.g. for HTTP the
543 `Content-Type` header value).
544
545#### `protocol`
546
547- Type: String
548- Description: The transport or application protocol used by the endpoint. This
549 specification defines a set of common protocol names that MUST be used for
550 respective protocol endpoints, but implementations MAY define and use
551 additional protocol names.
552
553 An example for an extension protocol identifier might be "BunnyMQ/0.9.1".
554
555 Predefined protocols SHOULD be referred to by name and version as
556 `<NAME>/<VERSION>`. The version number format is determined by the protocol
557 specification's usage of versions. If the version is not specified, the
558 default version of the protocol is assumed. For AMQP and MQTT, see the list
559 below. For others, refer to the protocol specifications.
560
561 The predefined protocol names are:
562 - "HTTP" - Used for HTTP/1.1, HTTP/2, HTTP/3.
563 - "AMQP/1.0" - Use the [AMQP 1.0][AMQP 1.0] protocol. MAY be shortened to
564 "AMQP". AMQP draft versions before 1.0 (e.g. 0.9) are *not* AMQP.
565 - "MQTT/3.1.1", "MQTT/5.0" - Use the MQTT [3.1.1][MQTT 3.1.1] or [5.0][MQTT
566 5.0] protocol. The shorthand "MQTT" maps to "MQTT/5.0".
567 - "NATS" - Use the [NATS][NATS] protocol.
568 - "KAFKA" - Use the [Apache Kafka][Apache Kafka] protocol.
569
570 All messages inside an Endpoint MUST use this same protocol.
571- Constraints:
572 - MUST be a non-empty case-insensitive string.
573 - SHOULD follow the naming convention `<NAME>/<VERSION>`,
574 whereby `<NAME>` is the name of the protocol and `<VERSION>` is the
575 version of the protocol.
576- Examples:
577 - `MQTT/3.1.1`
578 - `AMQP/1.0`
579 - `KAFKA`
580
581#### `protocoloptions`
582
583- Type: Map
584- Description: Configuration details of the endpoint related to the protocol
585 used to transmit the messages. An endpoint MAY be defined without detailed
586 configuration. In this case, the endpoint is considered to be "abstract".
587 For per-protocol option definitions, see [Protocol Options](#protocol-options).
588
589- Constraints:
590 - OPTIONAL.
591
592##### `protocoloptions.endpoints`
593
594- Type: Array of Objects
595- Description: An array of objects where each object describes one network
596 address at which clients can communicate with the endpoint. The object MAY
597 contain extension attributes that can be used by clients to determine which
598 address to use, or to configure access to the specific address. Whether the
599 address identifies a network host or links directly to a resource managed by
600 the network host is protocol specific.
601
602 The shape of each entry is customized for the protocol in use. For `HTTP`,
603 `AMQP/1.0`, `MQTT/3.1.1`, `MQTT/5.0`, and `NATS` the address is carried in a
604 `uri` attribute. For `KAFKA` the address is carried in a `bootstrap.servers`
605 attribute, which is an array of Kafka bootstrap server addresses, because
606 Kafka clients are configured with a bootstrap server list rather than with a
607 single destination URI.
608
609- Constraints:
610 - OPTIONAL.
611 - Entries are ordered by preference; the first entry is the preferred
612 address.
613 - Each object MUST carry the endpoint address in the attribute that the
614 endpoint's protocol defines for that purpose. Of the protocols defined in
615 this specification, `HTTP`, `AMQP/1.0`, `MQTT/3.1.1`, `MQTT/5.0`, and
616 `NATS` use a `uri` attribute holding a valid, absolute URI (URL), and
617 `KAFKA` uses a non-empty `bootstrap.servers` attribute. A protocol
618 defined outside of this specification MAY define a different addressing
619 attribute.
620- Examples:
621 - `[ {"uri": "https://example.com" } ]`
622 - ```
623 [
624 { "uri": "tcp://example.com" },
625 { "uri": "wss://example.com" }
626 ]
627 ```
628 - ```
629 [
630 { "bootstrap.servers": [ "broker1:9092", "broker2:9092" ] }
631 ]
632 ```
633 - ```
634 [
635 {
636 "uri": "tcp://example.com",
637 "priority": 1,
638 "status": "down"
639 },
640 {
641 "uri": "wss://example.com",
642 "priority": 2,
643 "status": "up"

648##### `protocoloptions.authorization`
649
650- Type: Array of Objects
651- Description: OPTIONAL authorization configuration details of the endpoint.
652 Each entry describes one authorization option that the endpoint accepts;
653 a client selects one of them. When specified, each entry MUST provide
654 sufficient metadata for clients to select the authorization mechanism
655 and discover where authorization is obtained. Runtime credentials and
656 deployment-specific values are expected to be supplied separately through
657 external configuration. The attribute names below MUST be used as
658 defined. Additional endpoint-specific extension attributes MAY be added.
659
660- Constraints:
661 - OPTIONAL.
662 - MUST be an array of objects if present.
663 - MUST only be used for authorization configuration.
664 - MUST NOT be used for credential configuration.
665
666###### `protocoloptions.authorization.type`
667
668- Type: String
669- Description: The type of the authorization configuration. The value SHOULD be
670 one of the following:
671 - `OAuth2`: [OAuth 2.0][RFC6749] authorization is used. The
672 [`authorityuri`](#protocoloptionsauthorizationauthorityuri) SHOULD
673 reference authorization server metadata as defined by [RFC 8414][RFC8414].
674 - `Plain`: The client uses a username with a plaintext password for
675 authentication and authorization. For HTTP, see the
676 [HTTP options](#http-options) `plainscheme`, `plainusernamefield`, and
677 `plainpasswordfield`; for other protocols, equivalent transport-specific
678 options MAY be defined as protocol extensions.
679 - `SASL`: The client uses a [SASL][RFC4422] authentication mechanism. The
680 [`mechanism`](#protocoloptionsauthorizationmechanism) attribute SHOULD be
681 provided when this type is selected.
682 - `X509Cert`: The client uses [X.509][RFC5280] client certificate
683 authentication and authorization.
684 - `APIKey`: The client uses an API key for authentication and
685 authorization. For HTTP, see the [HTTP options](#http-options)
686 `apikeyname` and `apikeyin`; for other protocols, equivalent
687 carrier-specific options MAY be defined as protocol extensions.
688
689- Constraints:
690 - OPTIONAL.
691 - MUST be a non-empty string if used.
692
693- Examples:
694 - `OAuth2`: `{ "type": "OAuth2", "authorityuri": "https://login.example.com/tenant/v2.0" }`.
695 This points clients to the OAuth 2.0 authorization server/issuer metadata.
696 - `Plain`: `{ "type": "Plain", "authorityuri": "https://docs.example.com/auth/plain" }`.
697 This points clients to product documentation for username/password-based authorization setup.
698 - `SASL`: `{ "type": "SASL", "mechanism": "SCRAM-SHA-256", "authorityuri": "https://docs.example.com/auth/sasl" }`.
699 This points clients to mechanism-specific setup guidance (for example SASL profile and parameter requirements).
700 - `X509Cert`: `{ "type": "X509Cert", "authorityuri": "https://docs.example.com/auth/x509" }`.
701 This points clients to certificate enrollment and trust-chain requirements.
702 - `APIKey`: `{ "type": "APIKey", "authorityuri": "https://docs.example.com/auth/apikey" }`.
703 This points clients to key provisioning and placement guidance (for example header/query usage).
704
705###### `protocoloptions.authorization.mechanism`
706
707- Type: String
708- Description: The SASL mechanism name for `authorization.type = "SASL"`, for
709 example `PLAIN` ([RFC4616][RFC4616]), `SCRAM-SHA-256` or `SCRAM-SHA-512`
710 ([RFC7677][RFC7677]), `OAUTHBEARER` ([RFC7628][RFC7628]), or `EXTERNAL`
711 ([RFC4422][RFC4422]). Mechanism names are those registered in the
712 [IANA SASL Mechanisms registry][IANA SASL Mechanisms].
713
714- Constraints:
715 - OPTIONAL.
716 - MUST be a non-empty string if used.
717 - MUST only be used when `protocoloptions.authorization.type` is `SASL`.
718
719###### `protocoloptions.authorization.resourceuri`
720
721- Type: URI
722- Description: The URI of the resource for which the authorization is
723 requested. The format of the URI depends on the authorization type.
724
725- Constraints:
726 - OPTIONAL.
727 - MUST be a non-empty URI if used.
728
729###### `protocoloptions.authorization.authorityuri`
730
731- Type: URI
732- Description: The URI of the authorization authority from which the
733 authorization is requested. The format of the URI depends on the
734 authorization type.
735
736- Constraints:
737 - OPTIONAL.
738 - MUST be a non-empty URI if used.

740##### `protocoloptions.deployed`
741
742- Type: Boolean
743- Description: If `true`, the endpoint metadata represents a public, live
744 endpoint that is expected to be available for communication.
745- Constraints:
746 - OPTIONAL.
747 - If present, MUST be either `true` or `false`, case-sensitive.
748 - When not specified, the default value MUST be `true`.

750#### `messagegroups`
751
752The `messagegroups` attribute is an array of URI to message definition groups.
753Relative references (beginning with `/`) are XIDs within the same registry.
754Absolute URIs reference message definition groups in external registries. The
755server stores absolute URIs as-is without resolving them.
756
757The `messagegroups` attribute is used to reference message definition groups
758that are not inlined in the endpoint definition.
759
760Example:
761
762```yaml
763{
764 "protocol": "HTTP/1.1",
765 "protocoloptions": {
766 "method": "POST"
767 },
768 "messagegroups": [
769 "/messagegroups/mygroup",
770 "https://other-catalog.example.com/messagegroups/external-group"
771 ]
772}
773```
774
775#### `messages`
776
777Endpoints are supersets of
778[message definition groups](./../../message-v1/docs/spec.md#message-definition-groups) and
779MAY contain inlined messages. See
780[Message Definitions](./../../message-v1/docs/spec.md#message-definitions).
781
782Example:
783
784```yaml
785{
786 "protocol": "HTTP/1.1",
787 "protocoloptions": {
788 "method": "POST"
789 },
790
791 "messagesurl": "...",
792 "messagescount": 1,
793 "messages": {
794 "myevent": {
795 "envelope": "CloudEvents/1.0",
796 "envelopemetadata": {
797 "attributes": {
798 "type": {
799 "value": "myevent"
800 }
801 }
802 }
803 }
804 }
805}
806```
807
808When this specification, and the [message specification](./../../message-v1/docs/spec.md),
809are used with specifications such as [CloudEvents](https://cloudevents.io),
810where a semantically unique identifier is used in a runtime message (e.g.
811CloudEvent's `type` attribute), it is STRONGLY RECOMMENDED that the
812`messageid` values of the message definitions for an Endpoint match that
813unique identifier and therefore be unique across all messages within the
814`messages` collection and the messages referenced by the `messagegroups`
815attribute. This will allow for an easy "lookup" from an incoming runtime
816message to its related message definition.
817
818However, there are times when this is not possible. For example, take the case
819where an Endpoint might have the same semantic message defined twice, once for
820a JSON serialization and once for an XML serialization. Using the same
821`messageid` value is not possible (even though the CloudEvent `type` attribute
822would be the same for both runtime messages), so the `messageid` value of one
823message definition (or the values of both) might not match the runtime
824message's `type` value. In those cases, finding the appropriate message
825definition will need to be done via examination of some other metadata - such
826as the message's
827`envelopemetadata.type` value along with its `envelopeoptions.format` value.
828These details are out of scope for this specification to define and are left as
829an implementation detail.
830
831Implementations MAY choose to generate an error if they detect duplicate
832`messageid` values across the `messages` collection message definitions and
833the `messagegroups` referenced message definitions, if that is the desired
834constraint for their users.

836#### Protocol Options
837
838For each protocol specified in the following sections there is a table that
839describes the set of protocol-specific options and the roles (Producer,
840Consumer, Subscriber) to which each option applies. All protocol options are
841OPTIONAL.
842
843The role applicability is descriptive: it guides clients on how to interpret
844metadata. Where a rule below is stated with MUST, MUST NOT, or REQUIRED, it
845is a conformance requirement of this specification, and a client evaluating
846the metadata MUST treat a violation as an error. A Registry server is not
847obligated to check these rules.
848
849In each table below, role applicability is shown as:
850- `✓`: The option applies to that role. Clients acting in that role SHOULD
851 apply the option semantics.
852- `-`: The option does not apply to that role.
853
854Any string value of any protocol option MAY contain placeholders expressed
855with the [RFC6570][RFC6570] Level 1 URI Template expression syntax, for
856example `orders/{tenantid}/events`. This applies to plain
857string values, to the string items of arrays, and to the keys and values of
858maps, and it also applies to the `uri` values of
859[`protocoloptions.endpoints`](#protocoloptionsendpoints). Placeholders are
860resolved out-of-band by the client; this specification does not define how
861the values are supplied. When the same placeholder name occurs in more than
862one value of the same endpoint, all of its occurrences MUST resolve to the
863same value.
864
865##### HTTP options
866
867The [endpoint URIs](#protocoloptionsendpoints) for "HTTP" endpoints MUST be
868valid HTTP URIs using the "http" or "https" scheme as defined in
869[HTTP Message Format].
870
871HTTP has no single connection that serves several roles, so each HTTP role is
872a distinct interface with its own request contract. This specification
873distinguishes three HTTP roles:
874
875- Subscription manager (`usage` = `["subscriber"]`): an endpoint that accepts
876 requests to create, modify, and delete subscriptions, for example an
877 implementation of the [CloudEvents Subscriptions API][CloudEvents
878 Subscriptions API]. It does not transfer messages.
879- Delivery target, also called webhook target (`usage` = `["producer"]`): an
880 endpoint that accepts messages pushed to it by an originator or by a
881 delivery agent.
882- Pull consumer (`usage` = `["consumer"]`): an endpoint from which a client
883 retrieves messages with its own requests.
884
885An "HTTP" Endpoint describes a profile for message and event transfer over
886HTTP, not a general-purpose HTTP API surface. Declaring exactly one role per
887Endpoint keeps the request contract of each interface unambiguous, so that a
888client knows what it can send and what it can expect without inspecting
889individual messages. Describing a general HTTP API is out of scope for this
890specification and is served by an API description language such as OpenAPI.
891
892Constraints:
893
894- An HTTP Endpoint MUST declare exactly one `usage` value and therefore MUST
895 represent exactly one of the three roles above.
896- An HTTP Endpoint MUST NOT declare `["subscriber", "consumer"]`.
897- A subscription manager, a delivery target, and a pull consumer that belong
898 to the same logical channel MUST be declared as separate Endpoint resources
899 and SHOULD be correlated with a shared `channel` value.
900
901| Name | Type | P | C | S | Description |
902|---|---|---|---|---|---|
903| `method` | string (HTTP method), default `POST` | ✓ | ✓ | ✓ | HTTP method for the concrete operation represented by the endpoint. |
904| `headers` | array of `{name: string, value: string}` | ✓ | ✓ | ✓ | HTTP request headers. Duplicate names are allowed. |
905| `query` | map of string to string | ✓ | ✓ | ✓ | HTTP query parameters for the operation. |
906| `apikeyname` | string | ✓ | ✓ | ✓ | Name of the API key carrier when `authorization.type` is `APIKey` (for example `x-api-key`). |
907| `apikeyin` | enum: `header`, `query`, default `header` | ✓ | ✓ | ✓ | Placement of API key metadata when `authorization.type` is `APIKey`. `header` SHOULD be used; `query` SHOULD only be used when header placement is not possible. |
908| `plainscheme` | enum: `basic`, `form`, `query`, default `basic` | ✓ | ✓ | ✓ | Transport pattern for `authorization.type` = `Plain`. `basic` refers to HTTP Basic authentication ([RFC7617][RFC7617]). |
909| `plainusernamefield` | string | ✓ | ✓ | ✓ | Parameter or header field name carrying the username when `plainscheme` is `form` or `query`. |
910| `plainpasswordfield` | string | ✓ | ✓ | ✓ | Parameter or header field name carrying the password when `plainscheme` is `form` or `query`. |
911
912These options only define protocol-level placement and naming metadata.
913Credential values (API keys, usernames, passwords) MUST NOT be stored in
914endpoint metadata and MUST be supplied out-of-band.

916##### AMQP options
917
918The [endpoint URIs](#protocoloptionsendpoints) for "AMQP" endpoints MUST be
919valid AMQP URIs using the "amqp" or "amqps" scheme. If the path portion of the
920URI is present, it MUST be a valid AMQP node name according to
921[AMQP Addressing Version 1.0].
922
923The following options are defined for AMQP endpoints.
924
925| Name | Type | P | C | S | Description |
926|---|---|---|---|---|---|
927| `node` | string | ✓ | ✓ | ✓ | AMQP node (address). When set, it overrides the URI path. |
928| `durable` | boolean, default `false` | ✓ | - | - | Whether the node identified by `node` is a durable node rather than a transient one. This is a property of the node. It is not the AMQP message header field of the same name and it is not terminus durability, which is expressed by `terminus-durability`. It does not by itself imply a delivery guarantee. |
929| `link-properties` | map of string to string | ✓ | ✓ | ✓ | AMQP link properties. |
930| `connection-properties` | map of string to string | ✓ | ✓ | ✓ | AMQP connection properties. |
931| `distribution-mode` | enum: `move`, `copy`, default `move` | - | ✓ | ✓ | AMQP source distribution mode. `move` means a transferred message is removed from the node and is therefore transferred to at most one receiver. `copy` means the message remains at the node after transfer and can also be transferred to other receivers. This describes distribution between the node and its receivers; it does not describe message locking. |
932| `connection-capabilities` | array of string | ✓ | ✓ | ✓ | AMQP connection capabilities. |
933| `node-capabilities` | array of string | ✓ | ✓ | ✓ | AMQP node capabilities. |
934| `source-filters` | map of string to any | - | ✓ | ✓ | AMQP source filter expressions/descriptor keys for receive setup. |
935| `dynamic` | boolean | ✓ | ✓ | ✓ | Dynamic node creation for source/target setup, depending on role. |
936| `terminus-durability` | enum: `none`, `configuration`, `unsettled-state` | ✓ | ✓ | ✓ | Durability mode for the applicable source or target terminus. For a `producer` endpoint this is the target terminus; for a `consumer` or `subscriber` endpoint it is the source terminus. |
937| `expiry-policy` | enum: `link-detach`, `session-end`, `connection-close`, `never` | ✓ | ✓ | ✓ | Expiry policy for the applicable terminus, selected as for `terminus-durability`. |
938| `timeout` | uinteger | ✓ | ✓ | ✓ | Timeout value used with terminus expiry policy. |
939| `sender-settle-mode` | enum: `unsettled`, `settled`, `mixed` | ✓ | ✓ | ✓ | AMQP sender settle mode requested for the link. It constrains the party that sends transfers over the link: the local client for a `producer` endpoint, the remote node for a `consumer` or `subscriber` endpoint. |
940| `receiver-settle-mode` | enum: `first`, `second` | ✓ | ✓ | ✓ | AMQP receiver settle mode requested for the link. It constrains the party that receives transfers over the link: the remote node for a `producer` endpoint, the local client for a `consumer` or `subscriber` endpoint. |

942An AMQP Endpoint MAY declare `["subscriber", "consumer"]`, because a single
943AMQP receiving link both establishes interest in the source node and carries
944the resulting transfers. When it does, the `subscriber` role refers to the
945establishment of the link with the node as source and the `consumer` role
946refers to the transfers over that link.

948##### MQTT options
949
950The [endpoint URIs](#protocoloptionsendpoints) for "MQTT" endpoints MUST be
951valid MQTT URIs using the (informal) "mqtt" or "mqtts" scheme. If the path
952portion of the URI is present, it MUST be a valid MQTT topic name as described
953by [MQTT 3.1.1] and [MQTT 5.0]. The informal
954schemes "tcp" (plain TCP/1883), "ssl" (TLS TCP/8883), and "wss"
955(Websockets/443) MAY also be used, but MUST NOT have a path.
956
957The following options are defined for MQTT 3.1.1 and MQTT 5.0 endpoints.
958
959| Name | Type | P | C | S | Description |
960|---|---|---|---|---|---|
961| `topic` | string | ✓ | - | - | Concrete publish topic name. |
962| `topicfilter` | string | - | - | ✓ | Subscribe topic filter. |
963| `qos` | enum: `0`, `1`, `2`, default `0` | ✓ | ✓ | ✓ | Role-relative QoS intent: publish QoS for producer, requested max QoS for subscriber, effective delivery QoS for consumer context. |
964| `retain` | boolean, default `false` | ✓ | - | - | MQTT retain flag for publish behavior. |
965| `willtopic` | string | ✓ | ✓ | ✓ | CONNECT Will topic configuration. |
966| `willmessage` | xid (message reference) | ✓ | ✓ | ✓ | CONNECT Will message definition reference. |
967
968Addressing constraints:
969
970- `topic` MUST be a concrete MQTT topic name. It MUST NOT contain the `+` or
971 `#` wildcard characters, since a wildcard is not a valid publish
972 destination.
973- `topicfilter` MAY contain the `+` and `#` wildcard characters as defined by
974 [MQTT 3.1.1] and [MQTT 5.0].
975- An MQTT Endpoint MUST NOT declare both `topic` and `topicfilter`.
976- An MQTT Endpoint MAY declare `["subscriber", "consumer"]`, because a single
977 MQTT connection both sends the `SUBSCRIBE` packet and receives the resulting
978 `PUBLISH` packets.
979
980MQTT 3.1.1 specific options:
981
982| Name | Type | P | C | S | Description |
983|---|---|---|---|---|---|
984| `cleansession` | boolean, default `true` | ✓ | ✓ | ✓ | MQTT 3.1.1 clean-session behavior for the connection. |
985
986MQTT 5.0 specific options:
987
988| Name | Type | P | C | S | Description |
989|---|---|---|---|---|---|
990| `cleanstart` | boolean | ✓ | ✓ | ✓ | MQTT 5 clean-start behavior for the connection. |
991| `sessionexpiryinterval` | uinteger (`0..4294967295`) | ✓ | ✓ | ✓ | MQTT 5 session expiry interval in seconds. |
992| `sharedsubscriptiongroup` | string | - | - | ✓ | Shared subscription group name. |
993| `nolocal` | boolean | - | - | ✓ | MQTT 5 subscribe no-local flag. |
994| `retainaspublished` | boolean | - | - | ✓ | MQTT 5 subscribe retain-as-published flag. |
995| `retainhandling` | enum: `0`, `1`, `2` | - | - | ✓ | MQTT 5 retain-handling mode. |
996
997
998Shared subscription constraints:
999
1000- `sharedsubscriptiongroup` MUST only be present when `topicfilter` is also
1001 present.
1002- The value of `sharedsubscriptiongroup` is the bare group name. It MUST NOT
1003 include the `$share/` prefix and MUST NOT contain the `/` character.
1004- When `sharedsubscriptiongroup` is present, a client MUST send the
1005 subscription as the topic filter `$share/{sharedsubscriptiongroup}/{topicfilter}`,
1006 where `{sharedsubscriptiongroup}` and `{topicfilter}` are the literal values
1007 of those two options.
1008
1009MQTT 5 Subscription Identifiers are runtime subscription state established by
1010the subscribing client. They are not endpoint metadata and are therefore not
1011defined as protocol options by this specification.

1013##### KAFKA options
1014
1015The [endpoint URIs](#protocoloptionsendpoints) for "Kafka" endpoints MUST be
1016valid Kafka bootstrap server addresses. The scheme follows Kafka configuration
1017usage as described in [Apache Kafka], e.g. `SSL://<HOST>:<PORT>` or
1018`PLAINTEXT://<HOST>:<PORT>`.
1019
1020The following options are defined for Kafka endpoints.
1021
1022| Name | Type | P | C | S | Description |
1023|---|---|---|---|---|---|
1024| `topic` | string | ✓ | ✓ | ✓ | Kafka topic name. |
1025| `acks` | integer (`-1..1`), default `1` | ✓ | - | - | Producer acknowledgement setting. |
1026| `key` | string | ✓ | - | - | Producer record key. |
1027| `partition` | integer | ✓ | ✓ | - | Fixed producer partition target or explicit consumer partition selection. |
1028| `consumergroup` | string | - | ✓ | - | Consumer group identifier for group-based consumption. |
1029| `headers` | map of string to string | ✓ | - | - | Producer record headers. |
1030| `keyserializer` | string | ✓ | - | - | Producer key serializer class/name. |
1031| `valueserializer` | string | ✓ | - | - | Producer value serializer class/name. |
1032| `autooffsetreset` | enum: `earliest`, `latest`, `none` | - | ✓ | - | Consumer offset reset behavior when no valid committed offset exists. |
1033| `enableautocommit` | boolean | - | ✓ | - | Consumer automatic commit behavior. |
1034
1035Kafka does not have a subscription primitive that is separate from
1036consumption; the group is the durable interest. This specification therefore
1037discriminates the two roles by the presence of `consumergroup`:
1038
1039- A `subscriber` Kafka Endpoint describes the creation and configuration of a
1040 consumer group as an act of registering interest. It MUST NOT declare
1041 `consumergroup`, since the group is the resource being established rather
1042 than a group to be joined.
1043- A `consumer` Kafka Endpoint describes joining an existing consumer group.
1044 It MUST declare `consumergroup` with a non-empty value.
1045- A Kafka Endpoint MUST NOT declare `["subscriber", "consumer"]`. The two
1046 roles MUST be declared as separate Endpoint resources and SHOULD be
1047 correlated with a shared `channel` value.
1048- `autooffsetreset` and `enableautocommit` describe group-based consumption.
1049 They MUST NOT be used on a `producer` or `subscriber` Endpoint.
1050- `autooffsetreset` expresses only the reset behavior when no valid committed
1051 offset exists. A concrete starting offset or a starting timestamp is runtime
1052 consumer state, not endpoint metadata, and MUST NOT be expressed through
1053 this option.
